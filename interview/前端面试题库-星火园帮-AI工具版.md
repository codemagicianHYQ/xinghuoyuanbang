## 一、项目总览与架构（高频必问）

### 1）请你介绍一下星火园帮项目和你负责的部分
**参考回答：**  
星火园帮是一个基于 uni-app 的微信小程序项目，我主要负责前端业务页面、统一请求层、登录鉴权链路、接口联调和线上问题排查。  
架构上是小程序请求先到 Nginx，再转发到 Node/Express，后端通过 Sequelize 操作 MySQL，部分场景使用 Redis，文件上传走 COS。  
我负责把前端调用、错误处理、token 生命周期和后端返回格式统一，保证业务页面开发效率和线上稳定性。

### 2）从点击登录到页面跳转，完整链路是什么？
**参考回答：**  
用户点击登录后先 `wx.login` 获取 code，前端通过封装的 `request()` 请求 `/auth/wechat-login`。  
请求经过 Nginx 反向代理到 Express，后端换取 openid，查询或创建用户，签发 JWT 并返回用户信息。  
前端收到后保存 token，更新登录态，再跳转首页；后续请求统一在 header 携带 token。

### 3）为什么做统一 request 封装？
**参考回答：**  
核心是把重复逻辑集中：baseURL 拼接、token 注入、401/4xx/5xx 处理、重试或续期策略。  
这样业务页面只关注数据和交互，不关心网络细节，后期改网关、改鉴权策略都只动一处。

### 4）你的前后端联调策略是什么？
**参考回答：**  
我先和后端确认接口契约（字段、类型、错误码、分页规则），再用 mock 跑主流程，最后换真接口联调。  
联调阶段重点验证四类状态：正常态、空态、异常态、权限态，避免只测 happy path。

### 5）你如何做接口异常处理？
**参考回答：**  
按层处理：网络层超时和断网、HTTP 状态码、业务 code。  
比如 401 触发登录态失效流程，503 做服务繁忙提示，关键操作失败会保留用户输入并支持重试，减少挫败感。

## 二、H5/前端工程能力（JD 对齐）

### 6）你如何保证 H5 页面性能？
**参考回答：**  
我会从资源、渲染、交互三层做优化：资源压缩与按需加载、减少不必要重渲染、首屏骨架屏和关键路径优先。  
业务里会重点优化列表和图片场景，比如懒加载、分页、缓存与节流，保证低端机可用性。

### 7）如何设计可维护的页面结构？
**参考回答：**  
按“页面容器 + 业务组件 + 基础组件”分层，样式采用可复用设计 token，状态管理只保留必要共享状态。  
避免把请求、渲染、业务判断混在一个超大组件里。

### 8）你做过哪些前端安全相关处理？
**参考回答：**  
前端侧避免把敏感信息写死，严格处理 token 生命周期，不在日志中打印隐私数据。  
对富文本和外部输入做基本过滤，关键权限校验放在后端，前端只做体验层保护。

### 9）如果需求很急，你如何保证质量？
**参考回答：**  
我会先保主链路可用，再拆分非核心优化为二期。  
同时维护最小回归清单：登录、核心下单/发布、消息、支付回调状态同步，确保不因赶工破坏主流程。

### 10）你如何做线上问题定位？
**参考回答：**  
先判断影响面并止损，再按链路定位：前端日志 -> 网关 -> 后端日志 -> 数据层。  
我会优先确认是接口失败、数据脏、还是前端状态机错误，避免盲修。

## 三、AI 开发经验（核心加分）

### 11）你在项目里怎么用 AI，而不是“只会问答”？
**参考回答：**  
我把 AI 放在四个环节：需求拆解、样板代码生成、问题排查、测试清单补全。  
例如我会让 AI 先输出“任务拆解 + 风险点 + 验收清单”，再进入编码；编码后再让 AI 审查边界条件和异常路径。

### 12）AI 生成代码你怎么保证可信？
**参考回答：**  
我有三道校验：业务正确性、架构一致性、真实运行验证。  
尤其是鉴权、支付、权限、数据删除相关逻辑，我不会直接采纳 AI 输出，必须人工审查和联调验证。

### 13）给一个 AI 提效的真实例子
**参考回答：**  
在统一请求层改造时，我用 AI 快速产出错误码分层处理模板和类型定义草稿。  
我再结合项目规范调整成统一拦截器，减少了重复劳动，把更多时间放在业务边界测试上。

### 14）AI 使用的边界是什么？
**参考回答：**  
不把生产密钥、用户隐私数据直接喂给模型；核心安全逻辑不做“无审查直出”。  
AI 负责提案和初稿，人负责决策和验收。

## 四、Claude Code 与 Cursor（重点追问题）

### 15）你怎么区分 Claude Code 和 Cursor 的使用场景？
**参考回答：**  
我通常把 Claude Code 用在“复杂问题拆解、跨文件重构建议、方案评审”这类高语义任务；  
Cursor 更适合“贴近代码上下文的快速实现、局部修改、边写边查”的工程执行。  
简单说：一个偏“深度思考与方案”，一个偏“IDE 内落地与迭代”。

### 16）你在 Cursor 里最常用的能力是什么？
**参考回答：**  
最常用三类：基于当前文件上下文改代码、跨文件定位引用关系、让它按已有代码风格补全测试或类型。  
我会给明确约束：只改哪些文件、不能改哪些行为、需要保留哪些接口兼容。

### 17）你如何写 Prompt 才能稳定产出可用代码？
**参考回答：**  
我会写“目标 + 约束 + 输入输出 + 不可变项 + 验收标准”。  
比如：只改请求层，不改业务组件；保留原接口签名；新增 401 统一处理；给出最小回归点。  
Prompt 越像任务单，结果越可控。

### 18）Cursor/Claude Code 给的方案冲突时怎么办？
**参考回答：**  
我会先回到项目约束：是否符合现有架构、是否影响上线风险、是否便于团队维护。  
若都可行，优先选改动面更小、回滚更容易的方案。

### 19）你怎么验证 AI 改动没有引入回归？
**参考回答：**  
先看 diff 是否超出任务边界，再跑核心流程联调，最后过一遍异常分支。  
我有固定回归点：登录态、列表分页、提交动作防重、失败重试、空态显示。

### 20）如果面试官质疑“AI 会让你代码能力退化”？
**参考回答：**  
我把 AI 定位成“加速器”，不是“替代器”。  
核心能力仍是架构判断、边界识别和问题闭环；AI 帮我节省的是重复体力劳动，不是工程决策。

### 21）你用 Claude Code 做过什么“复杂任务”？
**参考回答：**  
我会用它先做跨模块分析，比如请求链路、鉴权和错误处理的统一改造影响面。  
它擅长先给出“改造步骤 + 风险点 + 回滚策略”，我再在 Cursor 里分批实施，降低一次性改动风险。

### 22）你如何在团队中推广 Cursor/Claude Code？
**参考回答：**  
我会先沉淀可复用模板：需求拆解模板、接口改造模板、Bug 排查模板、Code Review 清单。  
推广重点不是“谁写得快”，而是“交付质量是否稳定、返工是否下降”。

## 五、Pencil / Stitch（页面设计与前端落地）

### 23）你为什么在页面设计上更倾向 Pencil？
**参考回答：**  
我更看重结构化和可迭代性。Pencil 对节点层级、组件复用和后续改版更友好，和前端组件化思维更接近。  
对于要持续迭代的业务页面，它能减少“视觉稿好看但工程难落地”的问题。

### 24）Stitch 的优势是什么？你为什么不是全程用它？
**参考回答：**  
Stitch 在快速探索视觉方向、产出初稿上很快。  
但进入开发阶段，我更需要结构化、可维护和可追踪的设计资产，所以会切到 Pencil 做稳定落地。

### 25）你如何把设计工具产物映射到前端组件？
**参考回答：**  
先抽共性组件（按钮、卡片、输入项），再做页面组装；  
把颜色、间距、字体抽成 token，避免写死；  
最后按业务状态做交互补全（加载、空态、错误态、禁用态）。

### 26）如果设计稿和实际业务冲突，你怎么处理？
**参考回答：**  
先给出冲突点和影响面，再提供两版方案：体验优先和交付优先。  
和产品确认优先级后落地，避免“前端自己拍脑袋改需求”。

### 27）面试官追问：为什么你说 Pencil 更适合工程化？
**参考回答：**  
因为它更容易形成“可复用结构”，不是只看最终图。  
工程化看的是后续 N 次改动成本，不是第 1 次出图速度。

## 十、数据库基础操作（上次吉利高频）

### 31）你会哪些常见数据库操作？
**参考回答：**  
日常就是增删改查：`INSERT / SELECT / UPDATE / DELETE`，在项目里主要通过 Sequelize 做。  
比如用户登录时先按 openid 查询，没有就创建用户；资料更新走按主键更新；列表页做分页查询和排序。

### 32）你在项目里怎么做分页查询？
**参考回答：**  
我会约定 `page` 和 `pageSize`，后端换算 `offset` 和 `limit`。  
查询时同时返回总数和当前页数据，前端根据总数判断是否还有下一页，避免重复请求。

### 33）什么场景会加索引？你怎么解释索引价值？
**参考回答：**  
高频筛选、排序、关联字段会加索引，比如用户 openid、任务状态+创建时间这类组合条件。  
索引本质是用空间换时间，能明显减少查询扫描范围，但写入会有额外成本，所以不会滥加。

### 34）你如何避免慢查询？
**参考回答：**  
先看查询条件是否命中索引，再看是否有 `select *`、是否有大范围无条件扫描。  
我会优先缩小查询列和查询范围，必要时做索引优化或拆分查询。

### 35）事务你怎么理解？前端岗为什么也要懂？
**参考回答：**  
事务保证一组操作要么全部成功，要么全部回滚，核心是数据一致性。  
前端虽然不直接写事务，但要理解后端事务边界，避免把“部分成功”当成“全部成功”去展示。

### 36）你碰到过数据不一致问题吗？怎么处理？
**参考回答：**  
碰到过弱网重试导致重复提交。  
处理上我做了前端提交防重，后端做幂等校验；并把“处理中/成功/失败”状态显示清楚，减少误操作。

### 37）左连接和内连接有什么区别？
**参考回答：**  
内连接只返回两边都匹配的数据；左连接会保留左表全部数据，右表没有就补 `NULL`。  
业务上“主数据必须保留”常用左连接，比如任务列表要保留任务主体，即使关联信息缺失也不丢行。

### 38）你在 Sequelize 里常用哪些能力？
**参考回答：**  
常用 `findOne/findAll/create/update/destroy`，以及 `include` 做关联查询、`transaction` 做事务。  
我会把复杂查询收敛到 service 层，避免路由里出现大量 SQL 细节，保证可维护性。

### 39）如果面试官让你写“查最近一周已完成任务”思路？
**参考回答：**  
条件是状态=已完成、时间范围是最近7天，按创建时间倒序，带分页。  
如果这个查询是高频接口，我会建议在状态和时间字段上做合适索引。

### 40）数据库题的 30 秒总结版
**参考回答：**  
我能完成常见 CRUD、分页、排序、条件筛选，也理解索引、事务和慢查询优化的基本原则。  
在星火园帮里我更关注“接口返回是否稳定可用、是否会重复提交、是否会出现数据状态不一致”，确保前后端体验一致。

## 十一、前端测试工具（Jest 等）专项

### 41）你用过 Jest 吗？主要测什么？
**参考回答：**  
用过，主要做单元测试和部分组件行为测试。  
典型场景是工具函数、数据转换函数、请求封装逻辑、边界条件判断，确保重构时不破坏已有行为。

### 42）Jest 和 Testing Library 分别解决什么问题？
**参考回答：**  
Jest 是测试运行器和断言框架，负责执行、mock、覆盖率；  
Testing Library 更强调从用户视角测试 UI 行为，比如是否显示文案、点击后状态是否变化，而不是测内部实现细节。

### 43）你如何测试异步请求逻辑？
**参考回答：**  
我会 mock 接口返回，分别覆盖成功、失败、超时三类结果。  
断言点包括：loading 状态切换、错误提示是否出现、成功后数据是否正确渲染。

### 44）你会怎么测 request 封装？
**参考回答：**  
重点测四块：URL 拼接是否正确、token 是否注入、不同状态码是否走对分支、401 是否触发登录态处理。  
这类测试稳定且收益高，能快速兜住全项目网络层行为。

### 45）你怎么做 Mock？会不会和真实环境差太多？
**参考回答：**  
我会用固定结构的 mock 数据，并保留一套契约样例与真实接口对齐。  
关键流程仍要做真联调，Mock 主要用来提升开发期反馈速度，不替代集成测试。

### 46）快照测试你怎么看？
**参考回答：**  
快照适合稳定、展示型组件，能快速发现意外改动。  
但我不会滥用，交互复杂组件更适合写行为断言，不然快照容易变成“机械更新”。

### 47）覆盖率怎么看？是不是越高越好？
**参考回答：**  
覆盖率是参考，不是目标本身。  
我更看关键路径是否被覆盖：登录、提交、防重、异常处理，而不是为了数字去测低价值代码。

### 48）你会在 CI 里怎么接 Jest？
**参考回答：**  
常见做法是提交或合并请求时自动跑测试，并设置基础门槛（如关键目录必须通过）。  
如果失败要阻断合并，避免带病代码进入主分支。

### 49）你如何向面试官证明你会测试，而不是背概念？
**参考回答：**  
我会直接举星火园帮场景：测试 request 封装 401 分支、测试弱网失败提示、测试提交防重逻辑。  
面试官更看你有没有“业务测试意识”，不是只会说 API 名称。

### 50）测试专项 30 秒总结版
**参考回答：**  
我把 Jest 用在高收益位置：工具函数、请求层、关键交互分支。  
测试目标是降低回归风险，特别是登录态、异常态和重复提交这类线上高风险场景。  
我会结合 Mock 提升反馈速度，再用联调和回归清单保证最终可信。

## 十三、AI 基础概念解析（Function Calling / MCP / RAG / Skills）

### 51）什么是 Function Calling？和普通对话有什么区别？
**参考回答：**  
Function Calling 是让模型在对话中“结构化地调用工具/函数”，而不是只返回自然语言。  
普通对话给的是建议，Function Calling 给的是“可执行参数”，例如让模型输出 `{"city":"杭州","date":"today"}` 去调用天气接口。  
核心价值是把 AI 接到真实系统能力上，实现“能说也能做”。

### 52）Function Calling 在前端场景能做什么？
**参考回答：**  
可以把用户自然语言转成前端可执行动作，比如筛选条件、表单填充建议、查询参数组装。  
我会让模型只输出受控字段，再由前端白名单校验，避免直接执行高风险指令。

### 53）Function Calling 的风险点是什么？
**参考回答：**  
主要风险是参数越权、幻觉参数和误调用。  
治理方式是：严格 schema 校验、权限校验、幂等与审计日志，关键动作加二次确认，不让模型直接越过业务规则。

### 54）什么是 MCP？你怎么向面试官解释？
**参考回答：**  
MCP 可以理解为“模型连接外部工具和资源的标准协议层”，让模型以统一方式访问文件、浏览器、数据库、内部服务。  
它的价值是把工具接入标准化，降低每个 AI 工具各写一套适配的成本。

### 55）MCP 相比“自己写一堆插件”好在哪？
**参考回答：**  
插件各自为政时，接入和维护成本高，权限边界也容易混乱。  
MCP 通过统一的工具描述和调用方式，把发现、调用、鉴权流程规范化，更适合团队长期维护。

### 56）MCP 在工程落地时你关注什么？
**参考回答：**  
我会重点看三点：权限隔离、工具 schema 稳定性、调用可观测性。  
换句话说，先确保“不会乱调”，再追求“调得快、调得准”。

### 57）什么是 RAG？为什么需要它？
**参考回答：**  
RAG（检索增强生成）是“先检索可信知识，再让模型基于检索结果回答”。  
它解决的是模型知识过期和幻觉问题，尤其适合企业私有知识库、项目文档问答、流程检索。

### 58）RAG 的基本流程是什么？
**参考回答：**  
一般是文档切分 -> 向量化建索引 -> 查询召回 -> 重排 -> 把上下文喂给模型生成答案。  
效果关键在切分质量、召回准确率和上下文控制，不是只看模型本身。

### 59）RAG 和微调（Fine-tuning）怎么选？
**参考回答：**  
知识更新频繁、要可追溯时优先 RAG；  
需要固定风格输出、特定任务模式学习时考虑微调。  
很多场景是 RAG + 轻量提示工程先做，足够后再评估微调成本。

### 60）RAG 常见问题和优化思路？
**参考回答：**  
常见问题是“召回不准、上下文太长、答案不稳定”。  
可通过优化切分粒度、加 metadata 过滤、重排模型、答案引用来源、拒答策略来提升可信度。

### 61）什么是 Skills？和 Prompt 模板有什么差别？
**参考回答：**  
Skills 可以理解为“可复用的任务能力包”，通常包含角色、步骤、约束和输出格式。  
Prompt 模板更像一次性指令；Skill 更像可复用 SOP，适合团队沉淀一致的执行方式。

### 62）你在开发里如何用 Skills？
**参考回答：**  
我会把高频任务沉淀成 Skill，例如：需求拆解、接口改造、Bug 排查、测试用例生成。  
这样新任务进来先套标准流程，再做个性化补充，能显著减少沟通和返工。

### 63）Agent、Workflow、Function Calling 三者关系是什么？
**参考回答：**  
Function Calling 是“单步调用工具”的能力；  
Workflow 是“固定流程编排”；  
Agent 是“能根据目标自主选择下一步动作”的执行体。  
项目里通常是三者组合，而不是只靠一种模式。

### 64）什么是 Prompt Injection？如何防？
**参考回答：**  
Prompt Injection 是外部输入试图篡改系统指令，比如诱导模型泄露系统信息或执行越权操作。  
防护上要做输入隔离、工具权限最小化、关键动作显式确认、输出审计和敏感信息脱敏。

### 65）你如何向业务方解释“AI 可用但不全自动”？
**参考回答：**  
我会把 AI 定义为“人机协作系统”：AI 负责加速，关键决策由人兜底。  
上线标准不是“能跑一次”，而是“可控、可审计、可回滚”。

### 66）AI 概念题 30 秒总结版
**参考回答：**  
Function Calling 解决“让模型调用系统能力”，MCP 解决“工具接入标准化”，RAG 解决“基于私有知识的可信回答”，Skills 解决“团队可复用的 AI 工作流”。  
我在工程里关注的不是概念本身，而是权限、安全、稳定性和可维护性，确保 AI 真正服务交付。

## 十四、AI 概念题高频追问（面试官压问版）

### 67）如果 RAG 检索到了错误内容怎么办？
**参考回答：**  
先做来源可信度分层，再做重排和置信度阈值。  
低置信度时触发拒答或要求用户补充信息，避免“胡说但自信”。

### 68）Function Calling 会不会被模型乱调用？
**参考回答：**  
会，所以要把“能不能调”从模型中剥离出来，由业务层做权限判断和参数校验。  
模型只负责提议调用，系统负责最终裁决。

### 69）MCP 接入越多工具越好吗？
**参考回答：**  
不是。工具越多，权限面越大、治理越复杂。  
我会按业务价值分层接入：先高价值低风险，再逐步扩展。

### 70）怎么衡量 AI 能力接入是否成功？
**参考回答：**  
看三类指标：效率（交付时长、返工率）、质量（线上问题率、回归缺陷）、体验（任务完成率、用户满意度）。  
如果只提速不提质，说明接入方式还没跑通。

## 十五、AI 工作流（重点详细版）

> 这一章是面试重点。建议你按“阶段 -> 输入 -> 输出 -> 工具 -> 风险控制”去讲，面试官会觉得你不是在堆概念，而是真能落地。

### 1）我在前端项目里的 AI 工作流全景（可直接背）

**阶段 0：需求澄清与验收定义**  
- 输入：PRD、设计稿、接口草案、上线时间  
- 动作：让 AI 先把需求拆成用户故事和验收条件，补全边界（弱网、空态、权限态）  
- 输出：任务拆解清单 + 验收 checklist + 风险列表  
- 工具分工：Claude Code 偏拆解和风险分析，Cursor 偏本地代码上下文补充  

**阶段 1：技术方案与改动边界**  
- 输入：现有代码结构、模块依赖、历史问题  
- 动作：让 AI 输出 2-3 个方案（最小改动/中等改造/长期方案）并比较成本  
- 输出：选型结论、影响文件列表、回滚策略  
- 风险控制：明确“不可改项”（接口签名、鉴权行为、关键埋点）

**阶段 2：实现脚手架和样板代码**  
- 输入：选定方案、编码规范  
- 动作：AI 生成类型定义、请求封装、组件骨架、重复模板代码  
- 输出：可运行初稿（不是最终版本）  
- 风险控制：关键逻辑不直上，先做人工 review

**阶段 3：联调与异常分支补全**  
- 输入：后端联调环境、接口文档、错误码  
- 动作：AI 辅助生成异常分支处理：401、超时、重试、重复提交防护  
- 输出：主路径 + 异常路径都可运行  
- 风险控制：至少验证 4 态：正常、空态、异常、权限

**阶段 4：测试生成与回归清单**  
- 输入：核心功能点、历史线上问题  
- 动作：用 AI 生成 Jest 用例草稿、Mock 数据和回归清单  
- 输出：关键路径测试（request 封装、登录态、提交防重）  
- 风险控制：覆盖率不是目标，关键风险点覆盖才是目标

**阶段 5：上线前质量门禁**  
- 输入：diff、测试结果、性能数据  
- 动作：AI 辅助做变更总结和风险复核，人工确认是否达到上线标准  
- 输出：上线说明、回滚预案、监控点清单  
- 风险控制：关键动作必须可回滚、可观测、可止损

**阶段 6：上线后复盘与技能沉淀**  
- 输入：线上数据、告警、用户反馈  
- 动作：AI 帮助归因和复盘结构化，沉淀成可复用 Skill/模板  
- 输出：下一次可复用的 SOP（需求拆解模板、排障模板、测试模板）  
- 风险控制：复盘必须落到规则，不只是会议结论

### 2）工具怎么分工（Claude Code / Cursor / Pencil / Stitch）

### 71）你在工作流里如何分配工具职责？
**参考回答：**  
我一般按“思考深度”和“落地距离”分工：  
Claude Code 负责复杂任务拆解、跨模块影响分析、方案比较；  
Cursor 负责在 IDE 内按代码上下文快速实现和迭代；  
Pencil 负责结构化设计与可迭代页面资产；

### 72）为什么不只用一个 AI 工具？
**参考回答：**  
单工具通常在某一环节强，但很难覆盖全链路。  
我用多工具不是“叠 buff”，而是把它们放在最适合的环节，最后用统一验收标准收口。

### 73）你如何避免多工具带来的上下文割裂？
**参考回答：**  
我会维护一份“单一事实源”：任务目标、不可变约束、接口契约、验收清单。  
每次工具切换都回到这份基线，避免越改越偏。

### 3）面试官最爱问的“AI 工作流细节追问”

### 74）你怎么写一个高质量 AI 任务单？
**参考回答：**  
结构固定为：目标、上下文、输入输出、约束、验收标准、失败处理。  
例如：只改 request 层；保留接口签名；新增 401 统一处理；给出最小回归清单。  
有了任务单，AI 输出会更稳定，也更容易 review。

### 75）你怎么判断 AI 结果可不可以合并？
**参考回答：**  
我用四个门槛：功能正确、边界完整、架构一致、可回滚。  
任何一项不满足都不合并，特别是权限和支付相关改动。

### 76）AI 工作流里的“人工价值”体现在哪？
**参考回答：**  
人工价值在决策和兜底：定边界、选方案、控风险、做最终验收。  
AI 可以加速生成，但不能替代对业务后果负责的人。

### 77）如果 AI 建议和你的经验冲突怎么办？
**参考回答：**  
我会做最小实验验证，用数据和回归结果决策，而不是凭感觉。  
冲突解决标准是：对当前业务最稳、改动面最小、维护成本最低。

### 78）AI 工作流最容易失败在哪？
**参考回答：**  
最容易失败在“没有约束直接让 AI 写整块代码”。  
正确做法是分阶段、分边界、分风险等级推进，先小步可验证，再逐步放大。

### 4）结合星火园帮的 AI 工作流实例（你可直接讲）

### 79）请讲一个你实际跑过的 AI 工作流案例
**参考回答：**  
以 request 层改造为例：  
第一步我让 AI 拆任务，明确要统一 URL 拼接、token 注入、401 处理和错误提示。

不要追求“一次生成完美代码”，要追求“可控地持续逼近正确结果”。  
把 AI 当成协作成员，用流程保障质量，而不是把质量寄托在某个模型上。

## 十六、星火园帮：如何用 AI 工具做 UI 与交互实现（面试高频实战题）

### 81）面试官问：你们星火园帮前端页面是如何用 AI 工具实现 UI 和交互的？
**参考回答（推荐主答）：**  
我在星火园帮里把 AI 用在“从设计到可交付页面”的完整链路，不是只生成一张图。

第二步是把设计资产工程化：我会用 Pencil 做结构化页面迭代，提炼按钮、卡片、表单项等可复用组件，再映射到 uni-app 组件。

第四步是联调和体验修正：结合真实接口调通状态流转，确保 UI 状态和后端返回一致，避免“页面好看但交互不闭环”。  
最后通过回归清单验证主路径和异常路径，确保上线稳定。

### 82）你说“AI 实现交互”，具体是实现了什么交互？
**参考回答：**  
主要是高频业务交互：列表筛选与分页、表单输入校验、提交态防重复、弱网失败重试、登录态失效跳转。  
这些交互我会先让 AI 产出初稿逻辑，再按实际业务规则和接口契约做人工修正，保证行为可控。

### 83）AI 在 UI 实现里最大的价值是什么？
**参考回答：**  
最大价值是把重复劳动前置自动化，比如样板样式、基础交互骨架、状态分支模板。  
这样我能把更多时间放在真正影响体验的部分：业务流程、边界条件、异常处理和性能细节。

### 84）为什么你还要手动改，不能让 AI 一次写完？
**参考回答：**  
因为 UI 和交互最终要对真实业务负责，AI 初稿不一定完全符合现有架构和接口细节。  
我会把 AI 定位成“高质量初稿生成器”，最终由人工做一致性、可维护性和风险收口。

### 85）你怎么保证 AI 生成的 UI 不偏离设计稿？
**参考回答：**  
我会先固定设计 token（颜色、字号、间距、圆角）和组件规范，再让 AI 生成代码。  
之后做视觉对齐和交互走查，重点看层级、点击热区、状态反馈和响应式表现，必要时逐项微调。

### 86）你怎么保证 AI 生成的交互不会引发线上问题？
**参考回答：**  
我会做三层保障：  
1）逻辑层：关键状态机和权限判断人工 review；  
2）测试层：Jest 覆盖 request 层和关键交互分支；  
3）上线层：有回滚方案和监控点。  
这样即使有问题也能快速止损。

### 87）如果面试官追问：给一个“UI+交互+AI”的具体页面例子
**参考回答：**  
比如登录/个人信息页：  
AI 先生成基础布局和表单交互骨架；  
我补上 token 生命周期、401 处理、失败重试和输入合法性校验；  
联调时对齐后端字段和错误码，确保提示文案、按钮状态、页面跳转一致。  
最终结果是页面开发更快，但关键体验和稳定性仍由人工把关。

### 88）这一题的 30 秒口语版
**参考回答：**  
在星火园帮里，我用 AI 做 UI 和交互不是“直接一键生成上线”，而是“AI 先产出结构化初稿，我再工程化落地”。  
设计上用 Pencil 管结构和复用，编码上用 Cursor/Claude Code 提速交互骨架，再按接口和业务规则手动收口。  
最后通过联调、测试和回归清单保证状态闭环与上线稳定。  
所以 AI 提升的是效率，质量和可交付性由流程和人工把控。

## 十七、Agent 原理与使用经验（重点补充）

### 89）什么是 Agent？和普通聊天机器人有什么本质区别？
**参考回答：**  
普通聊天更偏“问答”，Agent 更偏“面向目标执行任务”。  
Agent 通常会自己做任务分解、选择工具、执行动作、观察结果并迭代，直到达到目标或触发停止条件。  
所以它不是只会说答案，而是能在约束下“做事”。

### 90）Agent 的核心工作原理是什么？
**参考回答：**  
可以概括成一个闭环：**感知 -> 规划 -> 行动 -> 反馈 -> 再规划**。  
感知是读取上下文和环境状态；规划是拆子任务和决策下一步；行动是调用工具；反馈是看执行结果是否达标。  
这个循环不断重复，直到完成任务。

### 91）Agent 和 Function Calling、Workflow 的关系？
**参考回答：**  
Function Calling 是“单步调用工具”的能力；  
Workflow 是“预先编排好的固定流程”；  
Agent 是“可动态决策下一步”的执行体。  
实际工程里常见组合是：Agent 负责决策，Function Calling 负责执行工具，Workflow 负责关键流程的稳定编排。

### 92）Agent 为什么更适合复杂任务？
**参考回答：**  
复杂任务通常信息不完整、路径不固定，不能靠一次提示就做完。  
Agent 能边做边看结果再调整策略，适合多步骤、多系统、需要试错的场景，比如跨模块排查和端到端改造。

### 93）Agent 的短板和风险是什么？
**参考回答：**  
风险主要有三类：越权调用工具、目标漂移导致“做偏”、循环尝试造成成本上升。  
治理方法是：工具最小权限、明确停止条件、任务边界白名单、关键动作人工确认和审计日志。

### 94）你在项目里怎么用 Agent，不让它“失控”？
**参考回答：**  
我会先给 Agent 明确边界：目标、可改文件、不可改行为、验收标准。  
再按风险分层：低风险任务让 Agent 自动执行，高风险任务只给建议由人工确认。  
最后用 diff 审查和回归清单收口，确保改动可追溯。

### 95）你有实际的 Agent 使用经验吗？举个前端场景
**参考回答：**  
有。我会让 Agent 先扫描 request 相关调用点，输出统一改造清单（重复逻辑、错误处理分散点、潜在兼容风险）。  
然后分批执行低风险改动，比如提炼工具函数和类型；高风险部分（鉴权、支付相关）我手动改。  
这样既提高效率，也保证关键链路可控。

### 96）Agent 在前端研发流程里最适合放在哪些环节？
**参考回答：**  
最适合四类环节：需求拆解、跨文件影响分析、重复代码改造、测试清单生成。  
不适合直接独立处理权限、支付、数据删除等高风险业务最终决策。

### 97）如何衡量 Agent 用得好不好？
**参考回答：**  
我会看三个维度：  
1）效率：需求到可联调时间是否缩短；  
2）质量：回归缺陷是否下降；  
3）可控：改动是否可解释、可回滚、可审计。  
如果只是更快但错误更多，就不算用好。

### 98）Agent 题 45 秒口语版（建议背）
**参考回答：**  
我理解 Agent 的本质是“以目标为导向的动态执行系统”，核心闭环是感知、规划、行动、反馈。  
在工程上我会把 Agent 和 Function Calling、Workflow 组合使用：Agent 负责决策，工具调用负责执行，固定流程负责稳定性。  
实际使用时我非常强调边界和治理：最小权限、停止条件、关键动作人工确认、全程可审计。  
这样才能既拿到效率红利，又不牺牲交付质量和线上稳定性。
