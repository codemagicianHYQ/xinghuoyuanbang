## 一、项目与业务理解

### 1. 星火园帮项目

<span id="Q1"></span>**Q1：请用 2 分钟介绍一下星火园帮这个项目，包括面向谁、解决什么问题、你负责哪一块。**

**答：** 星火园帮是一个面向校园的互助服务平台，主要解决校内信息不对称和多样化的学生需求，包含任务悬赏、资源分享、二手市集等模块。用户端是微信小程序（uni-app），运营方使用 Vue3 + Element Plus 的管理后台，后端是 Node.js + Express，前后端分离。我负责整体前端开发，包括小程序的页面与交互、管理后台的搭建与业务页面、以及和后端一起定接口、联调与部署。项目从 2025 年 2 月做到 6 月，已上线运行。技术栈上我们有几条清晰的方案：**跨平台小程序**用 uni-app + Vue 实现任务发布、接单、资源互换、个人中心等核心模块，降低多端开发成本；**管理后台**用 Vite + Vue3 + Element Plus 做数据驱动、响应式的运营端，支持实时监控、权限管理、内容审核；**后端**用 Node + Express + Sequelize 提供用户、任务、认证、支付等 RESTful API，JWT 做认证与路由权限；**部署**用 Nginx 做反向代理和静态托管，配置 SSL 实现全站 HTTPS，部署过程中也独立解决过 Nginx 配置冲突、http2 指令弃用等问题。

<span id="Q2"></span>**Q2：前后端分离下，小程序端、管理后台、Node 服务三者是怎么配合的？请求从用户点击到数据库再回到页面，大致走哪几条路径？**

**答：** 小程序和管理后台都只负责展示和发请求，不直连数据库。所有数据通过 Node 提供的 RESTful API 获取：小程序请求统一走 `https://xinghuoyuanbang.top/campushelper/api/v1/...`，管理后台走 `/admin/api/v1/...`，在 Nginx 里根据路径转发到本机 Node 的 1112 端口。一条典型路径是：用户在小程序点「微信登录」 → 前端调 `request({ url: "/auth/wechat-login", method: "POST", data: { code, userInfo } })` → 请求经 Nginx 转发到 Node → auth 路由里用 code 换 openid、查/建用户、生成 JWT → 返回 token 和用户信息 → 前端存 token 和 userInfo，下次请求在 header 里带 token，后端用 JWT 中间件鉴权后查库返回数据。

<span id="Q4"></span>**Q4：项目里有没有遇到过「前端以为后端会这样返回、结果不一致」的情况？你是怎么排查和解决的？**

**答：** 有过。比如任务列表有时后端返回的是 `{ tasks: [] }`，有时是 `{ data: { list: [] } }`，前端按一种结构写死了就会报错。我的做法是：先用 Postman 或浏览器看实际响应结构，再在 request 的 success 里打印一次 res.data，确认字段名和层级；如果是历史接口不统一，就在前端做一层适配，把不同格式转成组件需要的结构，同时和后端约定后续新接口统一用一种格式，避免再出现两套结构。

<span id="Q8"></span>**Q8：JWT 存在哪里（前端）？每次请求怎么带上去？过期后你们是怎么处理的（如自动跳登录、弹窗）？**

**答：** 小程序端 JWT 存在本地存储，key 是 `userAuthToken_xh`，用 `uni.getStorageSync` 读写。每次请求在 `request.js` 里从 storage 取出 token，若没有 "Bearer " 前缀会补上，然后放在请求头 `header.token` 里发给后端。过期后后端返回 401，我们在 request 的 success 里统一处理：若是登录/获取用户信息等认证接口的 401，就清掉本地 token 和 userInfo；若是其他接口的 401，会弹窗提示「登录已过期，请重新登录」，用户点确认后清存储并跳转到登录页。另外我们支持 token 续期，后端在响应头里返回 `x-renewed-token` 时，前端会更新本地 token 并顺带调一次 `/auth/me` 刷新用户信息。

## 二、Vue 与前端基础

### 3. Vue 2/3

<span id="Q9"></span>**Q9：Vue 2 和 Vue 3 你实际都用过，能说下你在项目里用到的区别吗？例如组合式 API、响应式原理（Proxy vs defineProperty）。**

**答：** 小程序端是 Vue2 + Vuex，管理后台是 Vue3。Vue3 用组合式 API（setup、ref、reactive）组织逻辑，按功能拆更清晰，不像 Vue2 都堆在 data/methods 里。响应式上 Vue3 用 Proxy，可以监听数组下标和对象新增属性，Vue2 用 defineProperty 需要 Vue.set。另外 Vue3 的 Teleport、Fragment、多根节点等在实际开发里也用到过。两套都写过，对区别有体会。

---

**Vue2 vs Vue3 响应式总结（可对照记忆）**

| 特性       | Vue2              | Vue3    |
|------------|-------------------|---------|
| 技术       | Object.defineProperty | Proxy   |
| 新增属性   | 不支持（需 Vue.set） | 支持    |
| 删除属性   | 不支持            | 支持    |
| 数组监听   | 不完整（部分方法需特殊处理） | 完整    |
| 性能       | 较慢（递归遍历初始化） | 更快（懒代理） |

---

**面试标准回答：为什么 Vue3 比 Vue2 响应式更好？**

Vue2 使用 **Object.defineProperty** 实现响应式，只能监听**已有属性**，并且需要**递归遍历对象**做初始化。**新增、删除属性**监听不到，数组通过下标修改也监听不到，需要 Vue.set 或数组变异方法。Vue3 使用 **Proxy**，可以监听对象的**新增、删除**以及**数组下标、length 等变化**，同时采用**懒代理**（访问到某一层才代理那一层），减少初始化成本，所以**性能更好、能力更完整**。我们项目里管理后台用 Vue3，小程序用 Vue2，对两套的差异有实际体会。

---

<span id="Q9-1a"></span>**Q9-1a：Vue3 用 Proxy 做响应式，能说说 Proxy 的 get/set 里 target、key、value 分别是什么吗？**

**答：** **Proxy** 是 ES6 的代理，`new Proxy(target, handler)` 里 **target** 是被代理的原始对象，**handler** 里写 **get(target, key, receiver)** 和 **set(target, key, value, receiver)**。**get**：**target** 是原对象，**key** 是当前访问的属性名，在 get 里做依赖收集（记下谁用到了这个 key）。**set**：**target** 是原对象，**key** 是被设置的属性名，**value** 是要赋的新值，在 set 里先给 target 赋值再派发更新（通知依赖该 key 的 effect 重新执行）。**receiver** 一般是代理对象本身，和 `Reflect.get/set` 配合保证继承场景下 this 正确。详见《前端面试-基础概念解析》「Proxy 与 handler（target、key、value）」。

---

<span id="Q9-2"></span>**Q9-2：Vue2 和 Vue3 有哪些主要区别？Vue3 做了哪些改进？（完整版）**

**答：** 可以从几块说：**一、响应式**：Vue2 用 defineProperty 只能劫持已有属性，新增/删除和数组下标监听不完整，要 Vue.set；Vue3 用 Proxy，支持新增删除和数组，懒代理性能更好。**二、API**：Vue2 选项式（data、methods 分块），Vue3 推荐组合式 API（setup、ref、reactive），按功能组织、易复用。**三、生命周期**：Vue3 销毁阶段改为 onBeforeUnmount、onUnmounted，组合式里没有 beforeCreate/created，用 setup 代替。**四、模板**：Vue3 支持多根节点（Fragment）、Teleport、多个 v-model（如 v-model:title）；v-if 与 v-for 优先级改为 v-if 更高。**五、移除**：Vue3 移除 filter、$on/$off/$once、$children 等。**六、性能与生态**：Tree-shaking 更友好、虚拟 DOM 优化、TypeScript 支持更好，状态管理推荐 Pinia。更完整的对比表与说明见《前端面试-基础概念解析》「Vue2 与 Vue3 区别及 Vue3 改进」。

---

<span id="Q9-1"></span>**Q9-1：Vue 生命周期有哪些？在实际开发中什么时候用？（Vue 面试必考 + 满分答则）**

**答：**  
**Vue2 常见生命周期**：beforeCreate、created、beforeMount、mounted、beforeUpdate、updated、beforeDestroy、destroyed。  
**Vue3 组合式里**：没有 beforeCreate/created，setup 本身相当于在这两个之间执行；挂载前后用 onBeforeMount、onMounted；更新前后用 onBeforeUpdate、onUpdated；销毁前后用 onBeforeUnmount、onUnmounted。

**实际开发中什么时候用（结合项目）：**

- **created / setup 里**：组件实例刚建好、DOM 还没有，适合**取路由参数、读本地缓存、初始化非 DOM 依赖的数据**。我们管理后台 App.vue 里在 onMounted 里读 localStorage 的 admin-user-info 赋给 userInfo，若在 created 阶段做也可以，不依赖 DOM。
- **mounted / onMounted**：DOM 已挂载，适合**调接口拉首屏数据、初始化依赖 DOM 的库（如图表、地图）**。我们仪表盘 Dashboard 在 onMounted 里调 getDashboardSummary、getRecentTasks、getUserActivity 等，表格和图表渲染完再拿数据没问题；若要做「一进来就请求」也可以放在 created/onMounted，看是否依赖 DOM。
- **beforeUnmount / onBeforeUnmount**：组件即将销毁，适合**清定时器、解绑事件、取消未完成的请求**。我们小程序里若有轮询或 WebSocket，会在 beforeDestroy 里 clear 掉，避免离开页面后还在请求或报错。
- **updated / onUpdated**：数据变更且 DOM 已更新完，一般少用，只在「必须依赖最新 DOM 再做一次计算」时用（如根据列表高度算滚动），用不好容易死循环，所以项目里我们尽量用 computed 或 watch 替代。

总结：**生命周期不是背名字，而是知道「在哪个阶段 DOM 有没有、数据有没有、组件还在不在」，然后在该阶段做该做的事**——初始化数据用 created/setup，依赖 DOM 或首屏请求用 mounted，收尾用 beforeUnmount。这样答既说清有哪些，又说清在真实项目里什么时候用，容易拿高分。

<span id="Q10"></span>**Q10：Vue 里组件间通信你用过哪几种？星火园帮里用户信息（如昵称、头像）在多个页面要用，你是用 Vuex 还是别的方式？怎么设计的？**

**答：** 用过 props/emit、Vuex、以及本地存储。星火园帮里用户信息是全局要用的，所以用 Vuex：state 里存 hasLogin、userInfo、userToken，登录成功后 mutation 里把后端返回的 user 和 token 写进 state，同时用 `uni.setStorageSync` 持久化到本地（key 是 userInfo_xh、userAuthToken_xh），这样刷新或重启小程序也能恢复登录态。各页面通过 mapState 或 this.$store.state.userInfo 取，需要最新信息时再调接口拿一次并 commit 更新 store。简历里写的 Vuex/Pinia 都了解：Pinia 是 Vue3 官方推荐的状态管理，API 更简洁（没有 mutation、直接改 state，用 defineStore），若新项目用 Vue3 会优先考虑 Pinia；当前星火园帮小程序是 Vue2 所以用 Vuex。

<span id="Q10-1"></span>**Q10-1：Vue 里组件间传参有哪几种方式？路由传参呢？**

**答：** **组件传参**：父子用 **props** 传下去、**emit** 事件传上去；跨层级可用 **provide/inject** 或 Vuex/Pinia；兄弟可先到共同父组件再 props/emit，或用状态管理。**路由传参**：**query** 拼在 URL 上（如 `/detail?id=1`），用 `this.$route.query.id` 或 `useRoute().query.id` 取，刷新不丢；**params**（Vue Router 3 里可命名路由 params，刷新可能丢，看配置）。动态路由如 `/task/:id` 用 `$route.params.id` 取。我们项目里列表点进详情用 query 或动态路由传 id，组件间表单、列表数据用 props/emit 和 Vuex 配合。

---

<span id="Q10-1a"></span>**Q10-1a：Vuex 和 Pinia 有什么区别？为什么 Vue3 推荐用 Pinia？**

**答：** **Vuex**：有 **state、getters、mutations、actions**；改 state 必须通过 **mutation**（同步），异步逻辑放 **action** 里再 commit mutation。模块用 **modules** 拆，有命名空间。**Pinia**：用 **defineStore** 定义 store，里面写 state、getters、actions，**没有 mutation**，可以直接改 state 或在 action 里改，API 更简洁；多个 store 就是多个 defineStore，天然模块化；**TypeScript** 支持好，和 Composition API（如 useXxxStore()）搭配自然。Vue3 官方推荐 Pinia，可视为 Vuex 的下一代。我们星火园帮小程序是 Vue2 所以用 Vuex 存用户信息和 token；管理后台若要做全局状态会优先用 Pinia。详见《前端面试-基础概念解析》「Vuex 与 Pinia（状态管理）」。

---

<span id="Q11"></span>**Q11：v-if 和 v-show 的区别？什么场景下你会优先用 v-show？**

**答：** v-if 是条件渲染，为 false 时节点不在 DOM 里；v-show 是切换 display，节点一直在 DOM。所以频繁切换的用 v-show 更合适，比如 Tab 切换、折叠面板，避免反复销毁创建。一开始就几乎不展示的用 v-if 可以减首屏节点数。我们列表里「无数据」的占位、权限控制用 v-if，Tab 内容用 v-show。

---

<span id="Q11-1"></span>**Q11-1：v-bind 和 v-html 分别做什么？使用 v-html 要注意什么？**

**答：** **v-bind**（可简写 `:`）用来把**数据绑定到元素属性**上，如 `:href="url"`、`:class="{ active: isActive }"`，属性值会随数据变化。**v-html** 是把**字符串当作 HTML 插入**到元素里，相当于设置 innerHTML，适合渲染富文本。**注意**：v-html 只应用在**可信内容**上；若把用户输入或未过滤的接口数据直接交给 v-html，可能造成 **XSS（跨站脚本）**，需要先做转义或白名单过滤。项目里富文本若来自后台且已做安全处理，可用 v-html；属性绑定大量用 `:class`、`:style`、`:src` 等。详见《前端面试-基础概念解析》「Vue 常用指令（v-bind、v-html、v-if、v-show 等）」。

<span id="Q12"></span>**Q12：你说「组件化、模块化开发思维」，能举一个你拆组件拆得比较满意的例子吗？为什么这样拆？**

**答：** 比如任务卡片：列表页、详情页、我的发布等都要展示「一条任务」的摘要，我抽成了 TaskCard 组件，接收 task 和少量 props（是否显示操作按钮等），内部负责展示标题、赏金、状态、发布者头像等。这样列表页只负责拉数据和分页，渲染用 v-for + TaskCard，样式和逻辑都集中在一个组件里，改一处到处生效。再比如发布按钮、自定义导航栏也做了公共组件，避免多页重复写。

<span id="Q12-1"></span>**Q12-1：Vue 里组合式 API（Composition API）和选项式 API（Options API）分别是什么？你在项目里怎么选的？**

**答：** 选项式 API 是 Vue2 那种按选项组织代码：data、methods、computed、watch、mounted 等各写一块，逻辑按「类型」分。组合式 API 是 Vue3 推荐的写法，用 setup（或 `<script setup>`）配合 ref、reactive、computed、onMounted 等，按「功能」把相关逻辑写在一起。比如「用户信息」的获取、展示、更新可以都写在一段里，而不是 data 里放一块、methods 里放一块。我们小程序端是 Vue2，用的选项式；管理后台是 Vue3，用的组合式 API，逻辑复用和阅读都更顺手。Vue3 也兼容选项式，但新代码更推荐组合式。

---

<span id="Q12-2"></span>**Q12-2：组合式 API 里 ref 和 reactive 有什么区别？什么时候用 ref、什么时候用 reactive？结合你项目举例子。**

**答：** ref 可以包任意类型，在 script 里取值要用 .value，在模板里会自动解包；reactive 只能包对象，用的时候直接访问属性，不用 .value。reactive 解构会丢响应式，ref 解构不会。一般简单值（数字、字符串、布尔）和「需要整体替换」的引用用 ref，一组强相关的对象（如表单、筛选条件）用 reactive。**项目里**：管理后台登录页（LoginView.vue）里，`loginForm` 用 reactive({ email: '', password: '' })，因为两个字段是一起用的表单对象；`loading`、`loginFormRef` 用 ref，一个是布尔、一个是 DOM/组件引用。任务管理（TaskManager.vue）里，`currentTask` 用 reactive 存整份任务表单（标题、类型、赏金等），`searchParams` 用 reactive 存筛选条件；列表数据 `tasks`、`currentPage`、`loading` 用 ref，因为要整体替换数组或数字。

---

<span id="Q12-3"></span>**Q12-3：`<script setup>` 和 手写 setup() 函数有什么区别？你更常用哪种？**

**答：** `<script setup>` 是语法糖，里边的变量、函数自动暴露给模板，不用 return；顶层 await 也能用。手写 setup() 需要把模板用到的都 return 出去。`<script setup>` 更简洁，我们 Vue3 管理后台新组件基本都用 `<script setup>`，只有需要和选项式混用或拿 setup 的 props/context 做复杂逻辑时才用手写 setup 函数。

---

<span id="Q12-4"></span>**Q12-4：ref 在 script 里为什么要写 .value？模板里要不要写？**

**答：** ref 返回的是一个响应式引用对象，真实值存在 .value 上，在 script 里修改或读取都要用 .value 才能改到/拿到实际值。模板里 Vue 会自动解包 ref，所以直接写变量名就行，不用 .value。例如我们 App.vue 里 `userInfo` 是 ref，onMounted 里写 `userInfo.value = JSON.parse(...)`，模板里写 `{{ userInfo?.nickname }}` 即可；LoginView 里 `loading.value = true`，模板里 `:loading="loading"`。

---

<span id="Q12-5"></span>**Q12-5：计算属性（computed）是什么？和 methods 有什么区别？项目里你在哪些地方用了 computed？**

**答：** computed 是根据依赖的响应式数据算出来的「派生值」，有缓存：依赖不变时不会重新算，只有依赖变了才会重新计算。methods 是每次调用都执行。所以「根据已有数据推导出的值」用 computed 更合适，既能少算几次，语义也更清晰。**项目里**：App.vue 里根据当前用户角色决定是否显示「社区管理员」相关菜单，用 `isCommunityAdmin = computed(() => userInfo.value?.role === 'community_admin')`，这样 userInfo 从 localStorage 读出来赋值后，侧栏菜单自动按角色显隐。任务管理（TaskManager）里，根据当前选中的任务类型控制表单项显隐：`showExpressFields = computed(() => currentTask.taskType === 'express')`、`showTakeoutFields = computed(() => currentTask.taskType === 'tea_coffee')`，任务类型一改，表单项的 v-if 跟着变，用 computed 比在 methods 里写函数再在模板里调用更合适，也有缓存。

---

<span id="Q12-6"></span>**Q12-6：computed 和 watch 区别？什么时候用 computed、什么时候用 watch？**

**答：** computed 是「算一个值」，依赖变了自动重算，适合模板里要展示的派生状态。watch 是「监听某个值变化然后执行副作用」（调接口、弹窗、改别的数据等），适合有副操作的场景。例如：根据 taskType 推导表单项是否显示 → 用 computed；监听路由变化去拉新页数据 → 用 watch；监听表单某字段变化后调接口校验 → 用 watch。我们项目里「根据用户角色显隐菜单」用 computed，「根据任务类型显隐表单项」也是 computed；若要做「筛选条件一变就重新请求列表」，可以用 watch 监听 searchParams 再调 fetchTasks。

---

<span id="Q12-7"></span>**Q12-7：reactive 的对象如果解构出来会丢响应式吗？怎么在解构时保持响应式？**

**答：** 会丢。reactive 返回的是 Proxy，解构出来的是普通值，不再和原对象联动。要保持响应式可以：一、不解构，一直用 `obj.xxx`；二、用 toRefs 把对象的每个属性转成 ref，解构出来的仍是 ref，保留响应式，例如 `const { email, password } = toRefs(loginForm)`，模板里还是用 email、password，在 script 里要用 email.value。我们登录页的 loginForm 没有解构，直接 loginForm.email、loginForm.password 用，所以没遇到这个问题；若要在子组件里传单个字段又保持响应式，会考虑 toRefs。

---

<span id="Q12-8"></span>**Q12-8：除了 ref、reactive、computed，Vue3 响应式 API 里你还用过或了解哪些？**

**答：** 项目里主要用 ref、reactive、computed。还了解：**watch** / **watchEffect**，监听响应式数据做副作用；**toRef** / **toRefs**，把 reactive 的属性转成 ref，解构或传给子组件时保持响应式；**readonly**，包一层只读代理，防止子组件改源数据；**shallowRef** / **shallowReactive**，浅层响应式，深层不追踪，适合大对象或第三方实例。我们管理后台里列表、表单、权限派生用 ref + reactive + computed 就够用了，暂时没用到 shallow 或 readonly，但知道有这些 API，需要性能优化或约束修改时会考虑。

### 4. JavaScript

<span id="Q13"></span>**Q13：Promise 和 async/await 你在项目里怎么用的？比如并发请求多个接口（如任务列表和用户信息同时拉）你会怎么写？**

**答：** 项目里请求封装返回的就是 Promise，业务里普遍用 async/await。并发多个接口可以用 Promise.all，例如：`const [taskRes, userRes] = await Promise.all([request({ url: '/tasks', ... }), request({ url: '/auth/me', ... })])`，两个都成功才往下走，有一个失败会进 catch。若需要「谁先回来用谁」可以用 Promise.race。我们首页有同时拉任务列表和用户信息的场景，就是这样写的。

<span id="Q13-1"></span>**Q13-1：什么是宏任务和微任务？事件循环的执行顺序是怎样的？**

**答：** JavaScript 单线程，异步靠**事件循环**调度。**宏任务**由宿主发起，如 script、setTimeout、setInterval、I/O、UI 渲染；**微任务**如 Promise.then/catch/finally 的回调、queueMicrotask。每轮事件循环：执行一个宏任务 → **清空当前所有微任务** → 再取下一个宏任务。所以**微任务总在当前宏任务之后、下一个宏任务之前**执行。例如 `setTimeout(() => console.log(1), 0); Promise.resolve().then(() => console.log(2)); console.log(3);` 输出 **3 → 2 → 1**：同步 3，再微任务 2，再 setTimeout 宏任务 1。详见《前端面试-基础概念解析》「宏任务与微任务（事件循环）」。

<span id="Q14"></span>**Q14：ES6+ 里你日常用得最多的是哪些？解构、箭头函数、模块化在星火园帮里有典型用法吗？**

**答：** 最常用的是：解构赋值（从 res.data 里解构出 list、total）、箭头函数（请求回调、数组方法里保持 this）、const/let、模板字符串、async/await、import/export。例如请求成功里会写 `const { data, message } = res`，组件里 `import request from '@/common/request.js'`，用 export default 导出 store、request 等，整体都是 ES 模块。

---

<span id="Q14-1"></span>**Q14-1：var、let、const 有什么区别？什么是块级作用域和函数作用域？**

**答：** **var** 是函数作用域，会变量提升，同一函数内可重复声明，在 for/if 里声明的 var 会泄漏到整个函数。**let** 和 **const** 是 ES6 的，都是**块级作用域**（一对大括号 `{}` 内有效），有暂时性死区（声明前访问会报错），同一块内不能重复声明；const 声明后不能重新赋值，但引用类型内部属性可以改（如 `const obj = {}` 可以 `obj.name = 'x'`）。**函数作用域**指变量只在声明它的函数内有效（var 的行为）；**块级作用域**指变量只在声明它的块（如 if、for、单独 `{}`）内有效（let/const 的行为）。典型区别是 for 循环：`for (var i = 0; ...)` 里 setTimeout 回调拿到的 i 是循环结束后的 3；`for (let i = 0; ...)` 里每次循环是新的块，回调拿到的 i 分别是 0、1、2。我们项目里 ES6+ 代码都用 const/let，需要重新赋值用 let，不需要改的用 const，基本不用 var。

---

<span id="Q14-2"></span>**Q14-2：ES6 相对 ES5 有哪些重要新特性？你项目里常用哪些？**

**答：** 可以按几类说：**一、变量与作用域**：let、const，块级作用域，解决 var 提升和泄漏问题。**二、解构与字符串**：对象和数组解构（如 `const { data } = res`）、模板字符串、字符串/数组新方法（includes、find 等）。**三、函数**：箭头函数（不绑定 this，适合回调和数组方法）、默认参数、rest 参数。**四、异步**：Promise、async/await，替代回调地狱。**五、模块**：import/export（ES Module），替代 IIFE 或 CommonJS，便于打包和 tree-shaking。**六、其他**：class、扩展运算符、Object.assign、Map/Set、可选链 `?.`、空值合并 `??` 等。我们项目里请求用 async/await 和 Promise.all，接口返回用解构拿 data/message，组件里用 const/let 和 import/export，模板字符串拼 URL 或文案，箭头函数在回调和 map/filter 里保持 this，整体都是 ES6+ 写法。更完整的列表和说明见《前端面试-基础概念解析》里的「ES6 相对 ES5 的新特性」。

---

<span id="Q14-3"></span>**Q14-3：深拷贝和浅拷贝有什么区别？如何实现深拷贝？（面试高频）**

**答：** **浅拷贝**只复制第一层：基本类型拷值，引用类型（对象、数组）拷的是引用，所以改拷贝后的对象里的嵌套对象，原对象也会变。**深拷贝**是递归复制所有层级，新对象和原对象完全独立。浅拷贝常用：`Object.assign({}, obj)`、`{ ...obj }`、`[...arr]`、`arr.slice()`。深拷贝常见方式：一、**JSON.parse(JSON.stringify(obj))**，简单但函数、undefined、Symbol 会丢，Date 变字符串，循环引用会报错，只适合纯数据。二、**手写递归**，遍历时基本类型直接赋，引用类型递归拷贝，要处理数组、Date、循环引用（用 Map 存已访问对象）等。三、**lodash 的 cloneDeep**，兼容多种类型和循环引用。四、**structuredClone(value)**（现代环境），原生深拷贝，支持循环引用，不支持函数。项目里需要「备份一份数据、避免被修改」时用深拷贝，比如表单初始值、编辑前先拷一份列表项；简单一层复制用浅拷贝即可。更详细说明见《前端面试-基础概念解析》「深拷贝与浅拷贝」。

---

<span id="Q14-4"></span>**Q14-4：for...in 和 for...of 有什么区别？遍历数组、对象分别用哪个？**

**答：** **for...in** 遍历的是**键**（对象可枚举属性名、数组下标），会遍历到原型链上的可枚举属性，遍历数组时得到的是索引且顺序不保证，一般不推荐用 for...in 遍历数组。**for...of** 遍历的是**值**（数组元素、Map/Set 值、字符串字符），针对可迭代对象，普通对象不能直接用 for...of（默认不可迭代）。**遍历数组**用 for...of 或 forEach；**遍历对象**用 for...in 或 Object.keys/entries。项目里对接口返回的 list 做处理多用 forEach 或 for...of，对配置对象用 Object.keys 或 for...in。

---

<span id="Q14-5"></span>**Q14-5：箭头函数和普通函数有什么区别？什么场景用箭头函数？**

**答：** **this**：普通函数里 this 由调用方式决定（谁调用指向谁），箭头函数没有自己的 this，继承定义时所在作用域的 this，不能通过 call/apply/bind 改。**arguments**：普通函数有 arguments，箭头函数没有，用 rest 参数 `...args` 代替。**构造函数**：普通函数可以 new，箭头函数不能。**原型**：普通函数有 prototype，箭头函数没有。**使用场景**：回调、数组方法里需要保持「外层 this」时用箭头函数（如 map、setTimeout、请求回调），避免 that/self 或 bind；要当构造函数或需要 arguments 时用普通函数。项目里请求成功回调和 map/filter 里都用箭头函数，保证 this 指向组件或 Vue 实例。

---

<span id="Q14-6"></span>**Q14-6：JS 数组你常用哪些方法？哪些会改变原数组、哪些不会？**

**答：** **会改变原数组**：push、pop、unshift、shift、splice（增删改）、reverse、sort。**不改变原数组**：slice（截取/浅拷贝）、concat、map（遍历返回新数组）、filter（过滤）、reduce（归并）、find、findIndex、includes、flat、join；forEach 只遍历无返回值。**用途**：对接口 list 用 map 转结构、filter 筛数据、forEach/for...of 遍历；浅拷贝用 slice、concat 或 [...arr]；判断是否数组用 Array.isArray。项目里任务列表、用户列表处理都用 map/filter，分页拼接用 concat 或 push 到新数组。详见《前端面试-基础概念解析》「JS 数组常用方法」。

---

<span id="Q14-7"></span>**Q14-7：形参和实参有什么区别？实参比形参多或少会怎样？**

**答：** **形参**是函数定义时写的参数（如 `function fn(a, b)` 里的 a、b），用来接收调用时传入的值；**实参**是调用时实际传入的值（如 `fn(1, 2)` 里的 1、2），按顺序一一赋给形参。**实参多于形参**：多出的在普通函数里可用 **arguments** 或 **rest 参数** `...args` 取（箭头函数没有 arguments）。**实参少于形参**：未传入的形参为 **undefined**，可用**默认参数**如 `function fn(a, b = 0)` 兜底。**rest** 如 `function fn(a, ...rest)` 能把剩余实参收成数组。详见《前端面试-基础概念解析》「形参与实参」。

---

<span id="Q15"></span>**Q15：闭包是什么？能举一个你在项目里或写代码时用到的场景吗？**

**答：** 闭包是函数能访问它外部作用域的变量，即使外部函数已经执行完。典型场景是防抖/节流：用一个函数包住 timer，每次调用时 clear 掉上一次的 timer 再设新的，这个 timer 就是闭包里的变量。还有请求封装里，makeRequest 里用的 options、resolve/reject 在 success 回调里被引用，也形成闭包。我们有些搜索框、滚动加载会用防抖减少请求次数，里面就用到闭包保存 timer。

---

<span id="Q16"></span>**Q16：如何判断数组？`typeof []`、`Array.isArray([])`、`instanceof Array` 有什么区别？**

**答：** `typeof []` 得到 `"object"`，无法区分数组和普通对象。`instanceof Array` 在单全局环境下没问题，但在 iframe 或多全局（如小程序里不同环境）可能失效。最稳妥的是 `Array.isArray([])`，专门用来判数组，我们项目里对后端返回的 list 做判断时用 Array.isArray，避免不是数组时调 .map 报错。

<span id="Q16-1"></span>**Q16-1：防抖（debounce）和节流（throttle）分别是什么？区别在哪里？能举典型使用场景吗？**

**答：** 防抖是：事件触发后等一段时间，若这段时间内再次触发就重新计时，直到「安静」了指定时间才执行一次。适合「只关心最后一次」的场景，比如搜索框输入：用户连续输入时先不请求，停止输入 300ms 后再发请求。节流是：在一段时间内无论触发多少次，只执行一次，到时间后再触发再执行。适合「固定频率执行」的场景，比如滚动加载、窗口 resize、按钮防重复点击：滚动时每 200ms 最多执行一次判断「是否到底部」。区别总结：防抖是「停下来了才执行」，节流是「每隔一段时间执行一次」。

---

<span id="Q16-2"></span>**Q16-2：手写一个简单的防抖函数，并说明为什么需要闭包。**

**答：** 简单版示例：
```js
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
      timer = null;
    }, delay);
  };
}
```
需要闭包是因为：每次事件触发会执行 return 出来的函数，而 timer 必须在上一次和下一次调用之间保持同一个变量；如果不用闭包，timer 要么是全局变量（污染全局），要么每次都是新的（无法 clear 上一次）。用闭包把 timer 包在 debounce 作用域里，返回的函数一直引用同一个 timer，就能正确「重置计时」。

---

<span id="Q16-3"></span>**Q16-3：手写一个简单的节流函数（用时间戳或定时器实现都可以）。**

**答：** 时间戳版：第一次立即执行，之后按间隔执行。
```js
function throttle(fn, delay) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= delay) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```
定时器版：第一次 delay 后执行，之后每 delay 执行一次。
```js
function throttle(fn, delay) {
  let timer = null;
  return function (...args) {
    if (timer) return;
    timer = setTimeout(() => {
      fn.apply(this, args);
      timer = null;
    }, delay);
  };
}
```
滚动加载一般用时间戳版，希望「先执行一次」；按钮防重复点击可以用定时器版。面试能说清「节流是固定频率执行」并写出一种实现即可。

---

<span id="Q16-4"></span>**Q16-4：在 Vue 组件里如何使用防抖？例如搜索框输入后请求接口。**

**答：** 可以封装一个 debounce 方法，在 created 或 setup 里把请求函数包一层，再在输入事件里调用。选项式写法示例：`methods: { onSearch: debounce(function() { this.fetchList(); }, 300) }`，这样用户输入时只会触发最后一次 300ms 后的 fetchList。组合式里在 setup 里 `const onSearch = debounce(() => { fetchList(); }, 300)`，模板里 `@input="onSearch"`。也可以用 lodash 的 debounce，或自己写一个工具函数放在项目里复用。我们资源搜索、任务列表筛选都有用防抖，减少无效请求。

### 5. HTML 与 CSS 基础

<span id="Q16-5"></span>**Q16-5：如何定义一个块（block）并将其放到页面水平中心？如果还要垂直居中呢？**

**答：**  
**水平居中**常见几种方式：

1. **块级元素有宽度**：`margin: 0 auto;`。块要设 `width`（或 max-width），左右 auto 才能生效，把块挤到中间。
2. **Flex**：父元素 `display: flex; justify-content: center;`，子块会水平居中；若只有一个子元素，也可以子元素 `margin: 0 auto`。
3. **Grid**：父元素 `display: grid; justify-items: center;` 或 `place-items: center`（水平+垂直一起）。
4. **绝对定位**：子元素 `position: absolute; left: 50%; transform: translateX(-50%);`，父元素需 `position: relative`（或其它定位上下文）。

**水平 + 垂直都居中**常见写法：

1. **Flex**：父 `display: flex; justify-content: center; align-items: center;`（或 `place-content: center` 配合合适高度）。
2. **Grid**：父 `display: grid; place-items: center;`，父要有高度（如 100vh 或固定 height）。
3. **绝对 + transform**：子 `position: absolute; left: 50%; top: 50%; transform: translate(-50%, -50%);`，父 `position: relative` 且设高度。
4. **Flex + margin auto**：父 flex，子 `margin: auto`，也可实现水平垂直居中。

项目里管理后台的登录卡片、弹窗内容区，以及星火园帮网页的 hero 区域，都用过 flex 或 margin auto 做居中布局。

---

<span id="Q16-6"></span>**Q16-6：CSS 盒模型是什么？content-box 和 border-box 有什么区别？**

**答：** 盒模型描述一个元素占用的空间：由 content（内容）、padding（内边距）、border（边框）、margin（外边距）组成。**content-box**（默认）：`width`/`height` 只算内容区，设 `width: 200px` 再设 `padding: 20px`，实际占宽度是 200 + 20×2 = 240px。**border-box**：`width`/`height` 已经包含 padding 和 border，设 `width: 200px; padding: 20px`，总宽度仍是 200px，内容区会缩小。布局时用 `box-sizing: border-box` 更直观，很多项目会全局写 `*, *::before, *::after { box-sizing: border-box; }`，我们管理后台和星火园帮网页的样式里也这样统一过，避免算错宽高。

---

<span id="Q16-7"></span>**Q16-7：CSS 选择器优先级（权重）怎么比较？如果相同怎么办？**

**答：** 优先级从低到高大致是：通配符 `*` < 标签（如 div）< 类（.class）< ID（#id）< 内联 style < `!important`。同等级时，后写的覆盖先写的。一般数「个数」：内联 1000，ID 100，类/属性/伪类 10，标签/伪元素 1，但不必死记，记住「ID > 类 > 标签」「后写覆盖先写」「少用 !important」即可。项目里我们多用类名和 BEM 或语义化类，避免用 ID 做样式，减少优先级冲突；组件库（如 Element Plus）覆盖样式时用类名提高一点权重，而不是全局 !important。

---

<span id="Q16-8"></span>**Q16-8：Flex 布局常用属性有哪些？justify-content 和 align-items 分别管什么？**

**答：** Flex 是「弹性盒子」，父元素 `display: flex` 后，子元素按主轴/交叉轴排列。**主轴方向**：`flex-direction: row | column | row-reverse | column-reverse`。**主轴对齐**：`justify-content: flex-start | center | flex-end | space-between | space-around | space-evenly`，管「横排时水平方向、竖排时垂直方向」的对齐。**交叉轴对齐**：`align-items: flex-start | center | flex-end | stretch`，管「横排时垂直方向、竖排时水平方向」的对齐。子元素上常用 `flex: 1` 占满剩余空间，`flex-shrink: 0` 防止被压扁。我们管理后台侧栏、表格工具栏、登录卡片内部，以及星火园帮网页的导航、统计区，都用 flex 做对齐和均分。

---

<span id="Q16-8a"></span>**Q16-8a：Flex 布局里，如何把两个方块放在父元素的两侧（一左一右）？**

**答：** 父元素 `display: flex`。**方式一**：`justify-content: space-between`，两个子元素自动一左一右，中间留空。**方式二**：左侧元素不设 margin，右侧元素 `margin-left: auto`，会把右侧推到最右。导航栏「左边 logo、右边用户信息」、表头「左边标题、右边操作按钮」常用这两种。我们管理后台顶栏、星火园帮网页导航就是这样做的。

---

<span id="Q16-9"></span>**Q16-9：什么是语义化 HTML？为什么要用？能举几个标签例子吗？**

**答：** 语义化是用合适的 HTML 标签表达「内容含义」，而不是全用 div/span。好处：可访问性更好（读屏软件能理解结构）、SEO 更友好、代码可读性高。例如：`<header>` 页头、`<nav>` 导航、`<main>` 主内容、`<article>` 独立文章/卡片、`<section>` 区块、`<aside>` 侧边、`<footer>` 页脚、`<button>` 按钮、`<form>` 表单。列表用 `<ul>/<ol>+<li>`，标题用 `<h1>~<h6>`。星火园帮网页的 index.html 里用了 header、nav、section、footer 等，既方便样式又利于结构和 SEO。

---

<span id="Q16-10"></span>**Q16-10：display: block、inline、inline-block 有什么区别？**

**答：** **block**：块级，独占一行，可设 width/height、上下 margin 生效。**inline**：行内，不独占一行，宽高由内容撑开，设 width/height 无效，上下 margin 对布局影响小。**inline-block**：行内排列但像块一样可设宽高、上下 margin 生效，常用于「一排可点的小块」（如标签、图标按钮）。例如按钮用 `display: inline-block` 可以设固定宽高且和文字在同一行；导航里多个链接并排也常用 inline-block 或 flex。**延伸**：200px 宽的父元素里两个 100px 宽的 div 设 `display: inline-block` 时，理论上会并排；但 inline-block 之间若有 HTML 换行或空格，会渲染出**空白间隙**，总宽度可能超过 200px 导致第二个被挤到下一行，解决方式可去掉标签间空白、设 `font-size: 0` 或改用 flex。

---

<span id="Q16-11"></span>**Q16-11：position 有哪几种？absolute 是相对谁定位的？**

**答：** **static**（默认）：正常文档流。**relative**：相对自身原来位置偏移，占位保留。**absolute**：相对「最近一个 position 不为 static 的祖先」定位，不占文档流。**fixed**：相对视口定位，滚动不动。**sticky**：在阈值内像 relative，滚出视口像 fixed。做「块水平垂直居中」时常用父元素 `position: relative`、子元素 `position: absolute; left: 50%; top: 50%; transform: translate(-50%, -50%)`，这时 absolute 是相对那个 relative 的父元素定位的。

---

<span id="Q16-11a"></span>**Q16-11a：Sass/SCSS 用过吗？变量、嵌套、mixin 是什么？项目里怎么用的？**

**答：** 用过。Sass/SCSS 是 CSS 预处理器，写变量、嵌套、mixin 等再编译成 CSS。**变量**：`$primary: #0d9488;`，页面里统一用 `$primary`，改主题色只改一处。**嵌套**：选择器可以写在大括号里嵌套，减少重复写父选择器。**mixin**：一段可复用的样式块，用 `@mixin name { ... }` 定义，`@include name` 引用，可带参数，比如清除浮动、flex 居中、响应式断点。我们管理后台（星火园帮前端UI）里用 SCSS，`main.scss` 里定了 CSS 变量和全局样式，组件里用 `lang="scss"` 写嵌套和变量，颜色、圆角、阴影等统一用变量，改设计规范时只改一处。简历里写的「熟悉 CSS3 (Sass/SCSS)」在项目里就是这样落地的。

---

<span id="Q16-11b"></span>**Q16-11b：CSS3 你用过哪些特性？过渡、动画、渐变、阴影、圆角在项目里有用到吗？**

**答：** 常用 CSS3 特性：**过渡** — `transition: property duration timing-function`，hover 或状态改变时平滑变化；**动画** — `@keyframes` + `animation`，做加载动画、轮播等；**渐变** — `linear-gradient`、`radial-gradient`，做背景、按钮；**阴影** — `box-shadow`、`text-shadow`，做卡片、按钮立体感；**圆角** — `border-radius`；**变换** — `transform: translate/scale/rotate`，做位移、缩放、旋转。我们管理后台和星火园帮网页的现代化改版里，登录页、仪表盘卡片、按钮、导航都用了圆角、阴影、过渡（如 hover 时颜色或阴影变化），部分背景用了渐变，整体更统一。复杂页面布局和交互效果靠的就是这些 CSS3 特性配合 Flex/Grid。

---

<span id="Q16-11c"></span>**Q16-11c：BFC 是什么？有什么应用场景？**

**答：** BFC（Block Formatting Context）块级格式化上下文，是 CSS 渲染的一块独立区域，内部布局不影响外部。**触发条件**：根元素、`float` 不为 none、`position` 为 absolute/fixed、`display` 为 inline-block/flex/grid、`overflow` 不为 visible 等。**常见应用**：一、**清除浮动** — 父元素设 `overflow: hidden` 或 `display: flow-root`，子元素 float 时父不会塌陷；二、**防止 margin 折叠** — 两块之间 margin 会合并，给其中一个包一层并触发 BFC（如 overflow: hidden）就不会合并；三、**两栏自适应** — 一侧 float，另一侧用 BFC 与浮动不重叠，实现左右分栏。项目里遇到浮动塌陷或 margin 异常时，会通过触发 BFC 来修正布局。

---

<span id="Q16-11d"></span>**Q16-11d：Grid 和 Flex 有什么区别？什么时候用 Grid？**

**答：** **Flex** 是一维布局，管「行」或「列」一个方向上的排列与对齐，适合导航、表单单行、卡片横排等。**Grid** 是二维布局，同时管行和列，用 `grid-template-columns/rows` 定义网格，子项可以跨行跨列（`grid-column/row span`），适合整页或整块区域的「表格式」排版，如仪表盘多块统计区、图片墙、表单多列。我们管理后台仪表盘若用 Grid，可以 `grid-template-columns: repeat(4, 1fr)` 直接排四列卡片，再 `gap` 控制间距；列表、工具栏用 Flex 更顺手。总结：一维、线性排列用 Flex；二维、多行多列用 Grid。

---

<span id="Q16-11e"></span>**Q16-11e：什么是重排（reflow）和重绘（repaint）？如何减少它们对性能的影响？**

**答：** **重排**：元素几何属性（宽高、位置、边距等）或布局结构变化，浏览器要重新计算布局。**重绘**：颜色、阴影、可见性等变化，不改变布局，只重新绘制。重排成本高于重绘，且可能引发子节点和后续元素连锁重排。**减少方式**：一、少改会触发布局的属性（如 width、top、margin），多用 `transform`、`opacity` 做动画（只触发合成，不触发重排）；二、批量改 DOM 或样式时先 `documentFragment` 或离线改完再一次性插入，或读布局和写布局分开，避免「读-写-读」交替；三、用虚拟列表减少 DOM 数量；四、将频繁变化的元素设 `will-change: transform` 或单独层。Vue 的虚拟 DOM 和批量更新也在减少直接操作 DOM 带来的重排次数。

---

<span id="Q16-12"></span>**Q16-12：DOM 是什么？常用的 DOM 操作 API 你用过哪些？**

**答：** DOM（Document Object Model）是浏览器把 HTML 解析成的一棵节点树，JS 通过 DOM API 可以增删改查节点、改样式、绑定事件。常用操作：**查** — `document.getElementById`、`querySelector`/`querySelectorAll`、`getElementsByClassName`；**增** — `createElement`、`appendChild`、`insertBefore`；**删** — `removeChild`、`remove()`；**改** — `textContent`/`innerText`/`innerHTML`、`setAttribute`/`getAttribute`、`classList.add/remove/toggle`；**遍历** — `parentNode`、`childNodes`、`children`、`nextSibling`。还有事件：`addEventListener`、`removeEventListener`。Vue/React 里我们一般不直接操作 DOM，而是改数据由框架去更新视图；但做图表、地图、富文本等需要拿 ref（Vue 里 ref、React 里 useRef）拿到真实 DOM 再调第三方库。小程序里没有 DOM，是自定义组件和 data 驱动视图，逻辑类似「数据驱动」思维。

---

<span id="Q16-12a"></span>**Q16-12a：script 标签的 async 和 defer 有什么区别？什么场景用哪个？**

**答：** 都是用在 `<script src="...">` 上，控制脚本的**下载**和**执行**时机，减少对 HTML 解析的阻塞。**无属性**：下载和执行都会阻塞解析，执行完才继续解析。**defer**：脚本与解析**并行下载**，等 **HTML 解析完成后**再**按书写顺序**执行，不阻塞解析，适合依赖 DOM 或按顺序依赖的主业务脚本。**async**：脚本与解析并行下载，**下载完就执行**（可能打断解析），**不保证**多个 async 脚本的执行顺序，适合独立、不依赖 DOM 也不依赖其他脚本的（如统计、广告）。我们打包后的入口脚本通常用 defer 或放在 body 底部，保证 DOM 就绪再执行。详见《前端面试-基础概念解析》「script 的 async 与 defer」。

---

<span id="Q16-13"></span>**Q16-13：什么是虚拟 DOM？Vue/React 为什么要用虚拟 DOM？**

**答：** 虚拟 DOM 是用 JS 对象描述「真实 DOM 树」的一种结构，例如 `{ tag: 'div', props: { class: 'box' }, children: [...] }`。数据变化时，先根据新数据生成新的虚拟 DOM 树，再和上一次的虚拟 DOM 做 **diff（对比）**，算出最小变更，最后只把变更应用到真实 DOM 上，减少直接操作真实 DOM 的次数。**为什么要用**：一、直接频繁改真实 DOM 成本高（重排重绘），用虚拟 DOM 可以批量 diff 后一次性更新，更可控；二、用 JS 对象描述视图，可以跨平台（如 SSR、小程序、Weex）在非浏览器环境里渲染；三、给开发者「声明式写视图、数据驱动」的体验，不用手写增删改 DOM。Vue 的 template 会编译成 render 函数，产出 VNode（虚拟节点），再通过 patch/diff 更新真实 DOM；我们写的都是 template 和 data，底层就是虚拟 DOM 这一套。

---

<span id="Q16-14"></span>**Q16-14：虚拟 DOM 的 diff 大概是怎么做的？key 的作用是什么？**

**答：** 简单说，diff 是「同层比较」：新旧两棵虚拟 DOM 树从根开始，一层层对比。如果同一层节点类型（tag）一样，就复用并对比 props 和子节点；类型不一样就整颗子树替换。**key 的作用**：在列表（v-for、map）里，给每个节点一个稳定的 key，diff 时用 key 来匹配「哪个新节点对应哪个旧节点」，这样插入、删除、重排时能尽量复用真实 DOM，而不是「按位置」误判导致整段替换或状态错乱。所以 key 要**唯一且稳定**，最好用 id，不要用 index 做 key（列表会增删、排序时 index 会变）。我们项目里任务列表、表格行用任务 id 或记录 id 做 key，保证列表更新时 Vue 能正确复用和更新节点。

---

<span id="Q16-15"></span>**Q16-15：什么是 SPA（单页应用）？和传统多页有什么区别？**

**答：** SPA（Single Page Application）是**只有一个 HTML 页面**的应用：首次加载时把整份 JS 拉下来，之后路由切换（如从首页点到任务列表）**不再向服务器要新 HTML**，而是前端用 JS 根据路由（如 `/tasks`）切换要展示的组件，数据再通过接口请求。**和传统多页的区别**：传统多页每次点链接都向服务器请求新的 HTML 页面，整页刷新；SPA 只刷新「视图层」，通过路由 + 组件切换 + 接口拉数实现，体验更顺、前后端分离更彻底。我们管理后台就是 SPA：一个 index.html，用 Vue Router 做路由，切换菜单时只是换组件、再按需调接口，不会整页刷新。

---

<span id="Q16-16"></span>**Q16-16：SPA 的路由是怎么实现的？前端路由（hash 和 history）有什么区别？**

**答：** SPA 的路由是**前端自己维护**的：根据当前 URL 决定渲染哪个组件，不直接请求服务器。两种常见方式：**hash 模式**：URL 里带 `#`，如 `https://xxx.com/#/tasks`，改变的是 `location.hash`，不会发请求，兼容性好；**history 模式**：用 `history.pushState`/`replaceState` 改 URL，如 `https://xxx.com/tasks`，没有 `#`，但用户刷新或直接打开这个 URL 时，请求会发到服务器，需要服务器把这类路径都回退到 index.html（否则 404）。Vue Router 里用 `createWebHistory()` 就是 history 模式，用 `createWebHashHistory()` 就是 hash 模式。我们管理后台若部署在子路径或不想配服务器 fallback，会用 hash；若希望 URL 干净且能配 Nginx 的 try_files，就用 history。

---

<span id="Q16-17"></span>**Q16-17：SPA 有什么优缺点？首屏慢怎么优化？**

**答：** **优点**：切换页面无白屏、体验接近原生 App；前后端分离，接口统一；一套前端代码可复用。**缺点**：首屏要把主 JS 都拉下来，首屏可能偏慢；SEO 不友好（首屏 HTML 里内容少，爬虫看到的多是空壳），所以做官网、博客常用 SSR 或预渲染。**首屏优化**：代码分割（路由懒加载，如 `() => import('./views/Task.vue')`）、压缩与 Tree Shaking、CDN 放静态资源、关键接口尽早发请求（在根组件或首屏组件里请求）、骨架屏或 loading。我们管理后台做了路由懒加载，首屏只拉登录或仪表盘需要的 chunk，其它页面进到时再加载。

### 6. 网络与浏览器

<span id="Q17"></span>**Q17：小程序里请求后端接口，从发请求到拿到数据中间可能出什么问题？你们有做统一错误处理吗？比如 401、网络超时。**

**答：** 可能的问题有：网络断开或超时、后端 4xx/5xx、业务 code 非成功、跨域（小程序端请求同源一般没有）、证书问题等。我们统一在 request.js 里处理：超时设了 15 秒，fail 里提示「网络请求失败」；success 里根据 statusCode：200/201 且业务 code 为 0 才 resolve(data)，否则 toast 提示并 reject；401 清 token 并提示重新登录；400 尽量展示后端返回的 message；429 做重试或提示「请求过于频繁」；503 维护模式有专门弹窗。这样业务层只要 try/catch 或 .catch 处理逻辑错误即可。

---

<span id="Q17-1"></span>**Q17-1：你简历写熟悉 Axios，管理后台里是怎么封装请求的？拦截器用过吗？**

**答：** 管理后台（Vue3）里用 Axios 发请求。封装方式：创建一个 axios 实例，baseURL 配成接口前缀（如 `/admin/api/v1` 或完整域名），**请求拦截器**里从 localStorage 取 token 塞进 `headers.Authorization` 或 `headers.token`，统一加 content-type 等；**响应拦截器**里根据 status 和业务 code 统一处理：2xx 且业务成功就 return response.data，401 清 token 并跳登录，4xx/5xx 统一 toast 并 reject，这样业务层直接 await request.get('/xxx') 拿到的就是 data。小程序端没有用 Axios（环境限制），用的是 uni.request 封装的 request.js，思路一样：拦截器里统一带 token、统一处理错误。所以「熟悉 Axios」体现在：会用实例 + 拦截器做统一鉴权和错误处理，业务代码只关心接口路径和参数。

---

<span id="Q17-2"></span>**Q17-2：fetch 和 Axios 有什么区别？GET、POST 请求在前端一般怎么发？**

**答：** **fetch** 是浏览器原生 API，返回 Promise，用法如 `fetch(url, { method: 'GET' })` 或 `fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(data) })`。GET 参数拼在 URL 或 `?key=value`；POST 数据放 body，要自己设 Content-Type 和 JSON.stringify。fetch 只有网络错误才 reject，4xx/5xx 仍 resolve，要自己判断 `res.ok` 或 `res.status`。**Axios** 是库，支持拦截器、自动转 JSON、取消请求等，GET 用 `axios.get(url, { params })`，POST 用 `axios.post(url, data)`，业务层更简洁，我们管理后台用 Axios。**GET** 一般参数在 query，幂等、取数据；**POST** 数据在 body，非幂等、提交或创建。RESTful 里查用 GET、增用 POST、改用 PUT、删用 DELETE。详见《前端面试-基础概念解析》「fetch、Axios 与 HTTP 方法」。

---

<span id="Q18"></span>**Q18：跨域是什么？你们的管理后台（Vue）访问 Node 接口时有没有遇到跨域？怎么解决的？**

**答：** 跨域是浏览器同源策略导致的：协议、域名、端口任一不同就算跨域，脚本发请求会被限制。管理后台开发时是 localhost:5173，请求的是 xinghuoyuanbang.top 或同机 Node，端口/域名不同会跨域。解决方式有两种：一、后端 Node 里用 cors 中间件，把允许的 origin 配成白名单（如本地开发域名、线上前端域名），我们 server.js 里就配了 allowedOrigins；二、开发阶段用 Vite 的 proxy 把 /api 代理到后端，这样浏览器看到的是同源。生产环境前后端通常同域或后端开 CORS，我们线上是 Nginx 同域转发，没有跨域问题。

---

<span id="Q19"></span>**Q19：HTTPS 和 HTTP 的区别？你们上线用了 HTTPS，能简单说下 Nginx 里 SSL 证书是怎么配的吗？**

**答：** HTTP 是明文传输，HTTPS 在 TCP 之上加了 TLS/SSL，对数据加密并校验服务器身份，防止窃听和篡改。我们线上全站用 HTTPS，Nginx 里在 server 块里 listen 443 ssl，然后配置 ssl_certificate 指向证书文件（如 /etc/nginx/ssl/xinghuoyuanbang.top.crt），ssl_certificate_key 指向私钥，浏览器访问 443 时就会走加密。HTTP 的 80 我们做了 301 重定向到 HTTPS，保证请求都走安全链路。

---

<span id="Q20"></span>**Q20：浏览器从输入 URL 到页面展示，大致经过哪些步骤？（可结合你们项目的 API 请求、静态资源来说）**

**答：** 大致是：DNS 解析拿到 IP → 建立 TCP 连接（HTTPS 还有 TLS 握手）→ 发 HTTP 请求 → 服务器返回 HTML → 浏览器解析 HTML，遇到 link/script/img 再发请求拉 CSS/JS/图片等 → 执行 JS，可能再发 API 请求（比如我们管理后台加载后请求 /admin/api/v1/dashboard/summary）→ 拿到数据后渲染表格、图表。我们项目里就是：先加载 index.html 和打包后的 JS，JS 里 axios 请求接口，Nginx 把请求转到 Node，Node 查库返回 JSON，前端把数据填到页面完成展示。

## 四、Node 与后端理解（前端岗也会问一点）

### 8. Node / Express

<span id="Q25"></span>**Q25：Express 里中间件是什么？请求进来后，依次经过 CORS、body 解析、路由、鉴权，你能按顺序说下在你们项目里是怎么挂载的吗？**

**答：** 中间件就是一个函数 (req, res, next)，在请求和最终响应之间执行，可以改 req/res、做校验、或调用 next() 交给下一个。我们 server.js 里顺序大概是：先 helmet、请求日志 → 再 cors（白名单校验 origin）→ 静态资源 → 支付回调单独处理 raw body → express.json()、urlencoded 解析 body → 然后 app.use("/campushelper/api/v1", mainRoutes)，mainRoutes 里再挂各子路由；需要鉴权的路由在子路由上挂 verifyToken 中间件，先校验 JWT 再进控制器。所以整体是：安全/日志 → CORS → body 解析 → 路由 → 具体路由里可能还有鉴权中间件 → 控制器。

---

<span id="Q25-1"></span>**Q25-1：Express 里路由是怎么组织的？用户、任务、认证、支付等模块是怎么拆的？**

**答：** 我们按业务模块拆路由文件，每个模块一个 router，再在入口里挂到 app 上。例如：`auth.routes.js` 管登录、微信登录、token 续期、获取当前用户；`user.routes.js` 管用户信息、头像上传、资料更新；`task.routes.js` 管任务列表、创建、接单、完成、取消等；`order.routes.js` 或支付相关单独一个；上传、静态资源也可能单独路由。入口里类似 `app.use("/campushelper/api/v1/auth", authRoutes)`、`app.use(".../tasks", taskRoutes)`，这样路径清晰、职责分明，对应简历里「设计并开发了涵盖用户、任务、认证、支付等模块的 API」。需要鉴权的路由在各自 router 里对具体路径挂 verifyToken 中间件，公开接口（如登录）不挂。

---

<span id="Q25-2"></span>**Q25-2：Express 里错误处理怎么做的？有统一错误处理中间件吗？**

**答：** 有。控制器或 service 里出错时我们统一用 `next(err)` 把错误抛给后面，在**最后**挂一个「四参数」的错误处理中间件 `(err, req, res, next)`，在这里根据 err 的类型或 statusCode 统一返回格式，例如 `res.status(err.status || 500).json({ code: err.code || 500, message: err.message || '服务器错误' })`，这样前端拿到的永远是统一的 `{ code, data, message }`。有的错误是业务错误（如参数不合法、无权限），我们自定义一个 AppError 或直接 `next({ status: 400, message: 'xxx' })`，在统一中间件里区分 4xx 和 5xx。这样既能保证高可用、接口稳定，又方便前端统一处理。

---

<span id="Q26"></span>**Q26：RESTful 里 GET 和 POST 的区别？什么时候用 PUT？你们任务列表、创建任务、更新任务分别用的什么方法和路径？**

**答：** GET 幂等、取数据，参数在 URL；POST 非幂等、一般用于创建或提交，数据在 body。PUT 一般用于整体更新某资源。我们任务列表是 GET /tasks 带 query；创建任务是 POST /tasks，body 里任务信息；更新任务状态或内容用 PUT /tasks/:id 或类似的 PATCH。删除用 DELETE。这样语义清晰，后端也按方法做权限和限流。

---

<span id="Q27"></span>**Q27：JWT 的鉴权流程：后端怎么从请求里拿到 token、怎么校验、校验失败返回什么状态码？**

**答：** 我们前端把 token 放在请求头 header 的 token 字段（格式是 "Bearer xxx"）。后端鉴权中间件里从 req.headers.token 或 req.headers.authorization 取出，去掉 "Bearer " 后用 jwt.verify(token, secret) 解码，能解出 payload（如 userId、过期时间）就认为合法，把用户信息挂到 req.user，next() 进下一步；解不出或过期会抛错，中间件里 catch 后 res.status(401).json({ message: '未授权或 token 无效' })，不再 next。这样需要登录的接口挂上这个中间件即可。

---

<span id="Q27-1"></span>**Q27-1：你简历写「了解基于角色的访问控制（RBAC）」，能简单说下 RBAC 是什么？你们项目里有没有按角色控制权限？**

**答：** RBAC（Role-Based Access Control）是按**角色**分配权限：用户关联角色（如普通用户、社区管理员、超级管理员），角色再关联可访问的资源或操作（如「可审核任务」「可看全部用户」），判断时看「当前用户角色是否具备该权限」而不是直接枚举每个用户。我们项目里：小程序端有普通用户和社区管理员，管理后台有不同角色（如 community_admin），菜单和接口会根据角色显隐或鉴权——例如只有社区管理员能看到「社区管理」菜单、能调审核接口，后端在鉴权中间件里除了验 JWT 还会查用户角色，不符合的返回 403。没有做特别细的「权限-资源」表，但「用户-角色-接口/菜单」这条线是按 RBAC 思路做的。

---

<span id="Q28"></span>**Q28：Sequelize 是什么？你们用 Sequelize 操作 MySQL 时，有没有写过联表查询（如任务列表带发布者信息）？**

**答：** Sequelize 是 Node 的 ORM，用模型和 Promise 操作 MySQL，不用手写 SQL 字符串。我们用户、任务、订单等都有对应 model，查任务列表时会 include 发布者用户模型，例如 Task.findAll({ include: [{ model: User, as: 'publisher', attributes: ['id', 'nickname', 'avatarUrl'] }] })，这样一次查出任务和发布者信息，避免 N+1 查询。复杂统计或分表场景有时会用 query 写原生 SQL，但常规 CRUD 和关联都用 Sequelize。简历里说的「用 Sequelize 屏蔽原生 SQL 的复杂性，提高代码可读性和可维护性」就是这样：用模型和关联代替手写 join，改表结构时主要改 model，业务逻辑更清晰。

### 9. 部署与 Nginx

<span id="Q29"></span>**Q29：你说用 Nginx 做反向代理，能具体说下：用户访问 `https://xinghuoyuanbang.top/campushelper/api/v1/xxx` 时，Nginx 是怎么把请求转到 Node 的？**

**答：** 用户请求先到 Nginx 的 443，server_name 是 xinghuoyuanbang.top。配置里有 `location /campushelper/api/ { proxy_pass http://127.0.0.1:1112/campushelper/api/; ... }`，所以路径匹配到的请求会转发到本机 1112 端口，路径不变。Nginx 还会把 Host、X-Real-IP、X-Forwarded-Proto 等头传给 Node，Node 监听 1112，Express 收到后按 /campushelper/api/v1 挂载的 mainRoutes 去匹配具体路由，处理完再返回，Nginx 把响应返回给用户。整个过程用户只和 Nginx 通信，不知道后面是 Node。

---

<span id="Q30"></span>**Q30：Nginx 里配置过 `/api` 转发，如果前端请求路径是 `/campushelper/api/v1/...`，Nginx 的 location 一般怎么写？**

**答：** 我们写的是 `location /campushelper/api/ { proxy_pass http://127.0.0.1:1112/campushelper/api/; ... }`。这样请求 URI 是 /campushelper/api/v1/xxx 时，会完整转发到 1112 的 /campushelper/api/v1/xxx。若写的是 `location /api/` 且 proxy_pass 带 URI，例如 `proxy_pass http://127.0.0.1:1112/backend/`，那 /api/v1/xxx 会变成 /backend/v1/xxx。所以要根据前端实际请求路径来写 location，我们前端是 /campushelper/api/v1，所以用 /campushelper/api/ 匹配。

---

<span id="Q31"></span>**Q31：你们管理后台的静态资源（打包后的 HTML/JS/CSS）是 Nginx 直接托管还是也走 Node？**

**答：** 是 Nginx 直接托管。打包后的文件放在服务器某个目录（如 /var/www/admin），Nginx 里配置 location /admin/ { root /var/www; try_files $uri $uri/ /admin/index.html; }，这样访问 /admin/ 或 /admin/xxx 时先找对应文件，找不到就回退到 index.html，方便前端路由的 history 模式。API 请求再通过 location /admin/api/ 转发到 Node，所以静态资源和接口是分开的：静态走 Nginx 本地文件，接口走 Node。

---

<span id="Q31-1"></span>**Q31-1：Nginx 负载均衡你了解吗？你们项目里有用到吗？**

**答：** 负载均衡是把多台后端服务器组成一个逻辑整体，Nginx 作为入口把请求按策略（轮询、权重、ip_hash 等）分发给多台 upstream。配置上用 `upstream backend { server 127.0.0.1:1112; server 127.0.0.1:1113; }`，再在 location 里 `proxy_pass http://backend`。我们星火园帮目前是单机部署，一台 Node 跑 1112 端口，没有配多机负载均衡；但简历里写「熟悉 Nginx 进行反向代理、负载均衡」是指**有能力在需要时配置**：比如流量上来后可以加多台 Node，用 Nginx 做轮询或 ip_hash 做会话保持，静态资源也可以单独做负载或交给 CDN。反向代理和静态托管是当前项目里实际用到的，负载均衡是掌握概念、能在多机部署时上手配。

---

<span id="Q32"></span>**Q32：部署时遇到过 502、跨域、接口 404 吗？能说一个你排查和解决的过程吗？**

**答：** 遇到过 502。一般是 Nginx 能通但上游 Node 没起来或挂了。排查步骤：先看 Node 进程是否在跑（如 pm2 list）、端口 1112 是否在监听；再直接 curl 本机 1112 的接口，若本机都失败说明是 Node 或数据库问题；再看 Node 日志有没有报错（如数据库连接失败、未捕获异常）。有一次是 PM2 的入口文件配错了，改回 server.js 并重启就好了。跨域我们开发时用 Vite proxy 或后端 CORS 白名单解决；404 多数是路径或 Nginx location 没匹配到，对一下前端请求的 path 和 Nginx、Express 的路由前缀就能定位。

---

<span id="Q32-1"></span>**Q32-1：部署过程中遇到过 Nginx 配置问题吗？比如配置冲突、http2 指令弃用等，你是怎么解决的？**

**答：** 遇到过。**配置冲突**：比如同一 server 里多个 location 的匹配顺序或 proxy_pass 写法和预期不一致，导致请求被转到错误的上游或静态资源 404。解决方式是先理清「请求路径 → 应该进哪个 location」，把 /api 和静态资源的 location 分开，用精确前缀匹配，并注意 proxy_pass 末尾有没有斜杠会改变转发 URI；必要时用 `nginx -t` 测配置、逐步加 location 排查。**http2 指令弃用**：新版本 Nginx 里原来在 server 里写的 `http2 on` 等写法可能有变更或弃用，需要查当前 Nginx 文档，改成 listen 443 ssl http2 或官方推荐的写法，改完 reload 再验证 HTTPS 和 HTTP/2 是否正常。这些都是在 Linux 上独立部署、配置 SSL 和前后端分离时实际踩过的坑，解决后对 Nginx 反向代理和静态托管更熟，也保证了服务稳定运行。

## 五、工程化与协作

### 10. Git 与协作

<span id="Q33"></span>**Q33：你简历写「熟练使用 Git」，日常最常用的命令有哪些？拉代码、切分支、解决冲突的流程能说一下吗？**

**答：** 常用：git status、git add .、git commit -m "xxx"、git push、git pull；拉代码用 git pull origin main 或先 fetch 再 merge；切分支 git checkout -b feature/xxx 或 git switch -c feature/xxx；合并用 git merge 或 git rebase。解决冲突时：pull 或 merge 后提示冲突，打开冲突文件看到 <<<<<<< / ======= / >>>>>>> 标记，按需求保留或修改后 git add、git commit（merge 时）或 git rebase --continue（rebase 时），再 push。

---

<span id="Q34"></span>**Q34：如果同一文件你和同事都改了，产生冲突，你会怎么处理？**

**答：** 先拉最新代码（pull 或 fetch + merge/rebase），冲突后不要强行覆盖，打开冲突文件看清楚两边的改动，和同事沟通该保留哪段逻辑或如何合并，改完后删掉冲突标记，add 并完成 merge/rebase，再推上去。若冲突太多或逻辑复杂，可以约一起看一遍再改，避免误删别人代码。

---

<span id="Q35"></span>**Q35：有没有用过 Git 的 rebase 和 merge？能简单说下区别吗？**

**答：** merge 会多出一个合并提交，保留分支结构；rebase 是把当前分支的提交「挪到」目标分支最新提交之后，历史是线性的，没有合并节点。我们平时协作多用 merge，简单清晰；自己开发分支整理历史时有时用 rebase，让 main 上的提交更干净。注意 rebase 会改写提交历史，已经 push 过的分支尽量不要再 rebase，否则别人拉代码会乱。

### 11. 构建与工程

<span id="Q36"></span>**Q36：Vite 和 Webpack 在你理解里主要区别是什么？为什么 Vue3 项目常用 Vite？**

**答：** **Webpack**：以入口为起点递归分析依赖、形成依赖图，用 **loader** 转译各类文件（如 babel-loader、css-loader）、**plugin** 做优化和注入，开发和生产都要先打包再跑，项目大时冷启动慢；热更新只重编改动模块，但仍依赖整图。**Vite**：开发阶段**不打包**，用浏览器原生 ES Module，dev server 按需**即时编译**当前请求的模块（如 .vue 用 esbuild），所以冷启动和热更新都很快；生产用 **Rollup** 打包，tree-shaking 和体积都不错。Vue3 官方推荐 Vite，我们管理后台用 Vite，开发时用 `server.proxy` 把 /api 代理到 Node 解决跨域。更完整的对比见《前端面试-基础概念解析》「Vite 与 Webpack」。

---

<span id="Q36-1"></span>**Q36-1：Webpack 里 loader 和 plugin 有什么区别？Vite 开发时为什么快？**

**答：** **loader**：负责「单文件转译」，如 .js 用 babel-loader 转 ES5、.vue 用 vue-loader 转成 JS、.scss 用 sass-loader 转 CSS，一条规则对应一种文件类型，链式执行（从右到左或从下到上）。**plugin**：在「打包过程的生命周期」里做更宽泛的事，如 HtmlWebpackPlugin 生成 HTML、DefinePlugin 注入环境变量、压缩、代码分割等，不针对单文件。**Vite 开发快**：不预先打包，浏览器通过 import 直接请求模块，Vite 收到请求再按需用 esbuild 等即时编译当前文件并返回，只编译用到的，所以冷启动和热更新都快；生产才用 Rollup 做一次性打包。

---

<span id="Q37"></span>**Q37：npm 和 pnpm 你更常用哪个？pnpm 有什么特点你了解吗？**

**答：** 平时用 npm 多，pnpm 也用过。pnpm 用硬链接和内容寻址存依赖，同一版本的包只存一份，省磁盘，安装也快；依赖隔离做得更严，不会出现「没在 package.json 里声明却能 require 到」的情况，更规范。若项目没强制要求，我一般还是 npm，团队统一即可。

---

<span id="Q38"></span>**Q38：项目里 ESLint、Prettier 有用吗？如何保证多人写代码风格一致？**

**答：** 有在项目里配 ESLint 和 Prettier：ESLint 管语法和规范，Prettier 管格式。提交前可以跑一遍 lint 或配 husky + lint-staged 在 commit 时自动检查。这样能统一缩进、引号、分号等，减少无意义 diff，代码评审也轻松。若目前还没配全，可以说「有在部分项目里用，希望后续团队统一加上」。

## 六、场景与设计题（偏开放）

### 12. 场景题

<span id="Q39"></span>**Q39：星火园帮里「任务列表」要支持下拉刷新、上拉加载更多，你会怎么设计接口和前端逻辑？分页参数怎么传？**

**答：** 接口用 GET，带 page、pageSize（如 page=1&pageSize=10），返回 `{ list: [], total }` 或 `{ data: { list, total } }`。前端：下拉刷新时 page 置 1，请求后替换列表并关闭刷新动画；上拉加载时 page+1，请求后 append 到列表。要防重复请求（loading 或 lock），也要在已经拿完所有数据时（list.length >= total）不再请求。我们项目里任务列表就是这样做的。

---

<span id="Q40"></span>**Q40：如果管理后台某个列表页接口很慢，你会从哪些方面优化？（前后端都可以说）**

**答：** 前端：加 loading、骨架屏；能分页的做分页，减少单次数据量；能缓存的列表短时间不重复请求；表格大数据量考虑虚拟滚动。后端：给列表接口加索引、避免 N+1 查询（用 include 或 join）；只返回列表需要的字段；必要时做 Redis 缓存。先看是接口慢还是渲染慢（Network 看接口耗时），再针对性优化。

---

<span id="Q40-1"></span>**Q40-1：向下滑动、数据累计加载时如何避免卡顿？（长列表优化）**

**答：** **分页**：不要一次拉全量，用 page/pageSize 分页，每次只渲染当前页或「已加载的累计条数」。**虚拟列表**：只渲染可视区域 + 少量缓冲的 DOM，滚动时复用节点、更新数据，DOM 数量恒定，大数据量也不会卡。**节流**：滚动时用节流控制「判断是否到底、触发加载」的频率，避免一次滚动触发多次请求或多次计算。**防重复请求**：加载中加 lock，避免连续触发多次加载。我们任务列表用分页 + 上拉加载更多，没有做虚拟列表；若列表特别长（如上千条）会考虑虚拟滚动或后端分页限制单次条数。

---

<span id="Q40-2"></span>**Q40-2：页面顶部放一个固定按钮，点击后自动滚动到最上方，怎么实现？**

**答：** 按钮用 `position: fixed` 固定在右下或顶部一侧。点击时：**方式一** `window.scrollTo({ top: 0, behavior: 'smooth' })` 平滑回到顶部；**方式二** 若滚动容器不是 window，是某 div，则给该 div 设 ref，用 `containerRef.value.scrollTop = 0` 或 `containerRef.value.scrollTo({ top: 0, behavior: 'smooth' })`。我们星火园帮网页有「回到顶部」按钮，用的就是 scrollTo + smooth。

---

<span id="Q40-3"></span>**Q40-3：如何去除或隐藏滚动条但保留滚动能力？**

**答：** 完全禁止滚动用 `overflow: hidden`。**保留滚动、隐藏滚动条**：容器设 `overflow: auto` 或 `overflow-y: scroll`，再隐藏滚动条—— Firefox 用 `scrollbar-width: none`；Chrome 等用 `::-webkit-scrollbar { display: none }` 或 `width: 0; height: 0`。移动端可加 `-webkit-overflow-scrolling: touch` 保持滑动顺滑。弹窗、侧边栏里常用这种方式。

---

<span id="Q41"></span>**Q41：用户反馈「头像在手机上看不到、电脑上能看到」，你会从哪几个方向排查？（可结合你项目里 URL 编码、域名配置等）**

**答：** 我们实际遇到过：一是头像 URL 里路径有中文或文件名有空格，手机端解析不友好，后来后端对 URL 做了 encode，前端拿到的就是编码后的地址；二是小程序端要在微信公众平台配「下载文件合法域名」，没配的话手机真机无法加载外链图片；三是 HTTPS 证书问题，证书过期或链不全会导致手机端不加载。排查时先看接口返回的 avatarUrl 是否带中文/空格，再在手机浏览器直接打开该 URL 看能否访问，最后确认小程序后台域名和证书。

---

<span id="Q42"></span>**Q42：小程序里要做一个「实时消息提醒」（如新订单、新聊天），在不引入 WebSocket 的前提下，你会用什么方案？有什么优缺点？**

**答：** 可以用轮询：定时（如每 30 秒）调一个接口查未读数量或最新消息，有变化就更新角标或弹 toast。实现简单、兼容性好，但实时性差、请求多。可以按场景调节间隔（前台短、后台长），或用长轮询（服务端 hold 住请求，有数据再返回）稍微提高实时性。真正要「准实时」还是得上 WebSocket，但面试可以说「业务能接受几秒延迟的话先用轮询，后面再迭代 WebSocket」。

**Q43：星火园帮从 2 月做到 6 月，期间遇到的最大技术难点是什么？你是怎么解决的？**

**答：**（建议用 STAR 讲一个真实例子）例如：上线后用户反馈头像在手机端不显示。我先在电脑开发者工具里复现不了，用真机调试和日志发现接口返回的 URL 里路径有中文、文件名有空格，手机端对这类 URL 支持不好。然后和后端一起改：后端对生成的文件 URL 做 encode，前端展示时直接用；同时确认小程序后台配置了下载域名。改完再在真机验证，问题解决。通过这件事对「前后端协作排查、环境差异、小程序限制」有了更深理解。

**Q44：你说习惯从全局视角思考、会主动学后端，能举一个「因为懂一点后端，前端问题更快解决」的例子吗？**

**答：** 例如接口返回 401 时，我不仅在前端清 token 跳登录，还会想是不是后端 token 过期时间设太短、或续期逻辑没生效。有次发现是后端返回的响应头里 x-renewed-token 没带上，导致前端一直用旧 token。因为懂一点 JWT 和响应头，我直接和后端说「麻烦在鉴权通过时把新 token 放到 x-renewed-token 头里」，后端改完前端配合存一下，登录态就稳了。这类问题若只懂前端，可能要猜很久。
